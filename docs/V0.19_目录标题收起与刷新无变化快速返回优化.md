# 语迹 V0.19 目录标题收起与刷新无变化快速返回优化

状态：已实施

日期：2026-06-18

## 1. 修改目标

V0.19 基于 V0.18，做两类优化：

```text
优化左侧目录区、标题区布局：支持目录区/标题区彻底收起和展开，减少横向占用。
优化顶部和搜索工具栏文案：进一步节省空间，降低误解。
优化刷新性能：针对无新增记录的刷新，避免不必要的完整重写，特别改善本机 Claude 和外部 codex_chat 小来源的刷新体感。
```

本版本不改变：

```text
来源体系。
会话解析格式。
搜索语义。
回复框命令。
备注功能。
正文 Markdown 渲染。
导出 MD 和复制全文。
```

## 3. 左侧区标题和收起/展开

### 3.1 标题文案

将：

```text
第一层：目录
第二层：标题
```

改为：

```text
目录
标题
```

目的：

```text
节省横向空间。
降低层级说明占用。
当前界面已经通过位置表达层级，不需要再写“第一层/第二层”。
```

### 3.2 收起按钮位置

在：

```text
目录
标题
```

右边分别新增一个按钮。

建议显示：

```text
目录 [收起]
标题 [收起]
```

按钮可以使用短文案或图标：

```text
收起 / 展开
‹ / ›
```

推荐优先使用文字按钮：

```text
收起
展开
```

原因：

```text
含义最明确。
不需要用户猜图标方向。
后续再做视觉精简也容易。
```

### 3.3 收起行为

目录区收起后：

```text
目录区整个 pane 彻底消失。
不保留窄竖栏。
不保留占位宽度。
省出来的宽度全部给标题区和会话区。
原“收起”按钮变成“展开”按钮。
```

标题区收起后：

```text
标题区整个 pane 彻底消失。
不保留窄竖栏。
不保留占位宽度。
省出来的宽度全部给会话区。
原“收起”按钮变成“展开”按钮。
```

这里的“原按钮变成展开”建议实现为：

```text
在父级 shell 或 header 中保留一个轻量的 collapsed-controls 区域。
目录收起时显示“展开目录”按钮。
标题收起时显示“展开标题”按钮。
展开后按钮消失，原 pane 恢复。
```

原因：

```text
pane 已经彻底消失，按钮不能继续放在消失的 pane 内。
需要在不会被隐藏的位置提供恢复入口。
这个入口就是原收起动作对应的展开按钮。
```

### 3.4 收起状态持久化

建议持久化：

```text
localStorage 保存目录区/标题区是否收起。
刷新页面后保持上次状态。
```

建议键名：

```text
Yuji.sidebarCollapsed.workspaces
Yuji.sidebarCollapsed.titles
```

默认状态：

```text
首次打开两个区都展开。
```

### 3.5 交互边界

允许状态：

```text
目录展开，标题展开。
目录收起，标题展开。
目录展开，标题收起。
目录收起，标题收起。
```

两个都收起时：

```text
会话区占满主要宽度。
顶部或会话区左上角显示“展开目录”“展开标题”两个按钮。
```

切换来源、刷新、搜索时：

```text
不强制展开目录区或标题区。
保留用户当前收起状态。
```

但如果用户执行会导致必须选择会话的操作：

```text
不自动展开左侧区。
仅保持当前会话或空状态提示。
```

## 4. 顶部统计文案

当前：

```text
会话：2100
目录：78
归档：32
含图：104
时间：2026-06-18 10:13:05
```

修改为：

```text
会话：2100
目录：78
归档：32
含图：104
2026-06-18 10:13:05
```

也就是：

```text
去掉“时间：”。
```

说明：

```text
顶部统计顺序固定，最后一项天然就是生成时间。
去掉“时间：”可以节省空间。
```

可选保留：

```text
statGenerated 的 title 或 aria-label 可以保留“生成时间：2026-06-18 10:13:05”。
```

但界面可见文字不显示“时间：”。

## 5. 搜索工具栏按钮顺序

当前 V0.18 顺序：

```text
搜索框
显示：全部 / 提问
搜索：全部 / 当前
工具按钮
```

V0.19 修改为：

```text
搜索框
搜索：全部 / 当前
显示：全部 / 提问
工具按钮
```

原因：

```text
全部/当前 是搜索范围，和搜索框关系最直接。
把它紧挨搜索框，用户更容易理解是在控制搜索范围。
全部/提问 是显示模式，放在后面更合理。
```

视觉建议：

```text
两个按钮组继续保持分组边框/间距。
不要把四个按钮视觉上混成一组。
```

语义不变：

```text
搜索：全部 = 当前来源下所有会话。
搜索：当前 = 当前打开会话。
显示：全部 = 显示当前会话全部正文内容。
显示：提问 = 只显示提问。
```

## 6. 刷新变慢的已完成检查结论

本项不是“待检查”，已基于 V0.18 做过必要检查后形成结论。

### 6.1 现象

用户反馈：

```text
相比之前，刷新时间明显变长。
尤其是 来源 Claude 或外部 codex_chat 时，本来记录很少，但刷新仍较慢。
刷新过一次之后，再次刷新理论上无新增记录，但仍然较慢。
```

### 6.2 已检查到的事实

当前运行数据体积大致为：

```text
local-claude:
  data 约 0.06 MB
  search 约 1.13 MB
  cache 约 1.16 MB
  detail 约 38 个文件

external-codex_chat_records_20260531_172954-ea9fda02:
  data 约 0.15 MB
  search 约 4.75 MB
  cache 约 4.81 MB
  detail 约 73 个文件

local-codex:
  data 约 3.52 MB
  search 约 296.17 MB
  cache 约 298.14 MB
  detail 约 2100 个文件
```

关键代码位置：

```text
Build-CodexChatIndex.ps1 1666 附近：
  Incremental/Current 会读取旧 CodexChatIndex.cache.json。

Build-CodexChatIndex.ps1 1737 附近：
  外部来源刷新会递归扫描来源目录下 *.jsonl。

Build-CodexChatIndex.ps1 1744-1750 附近：
  local-claude 会递归扫描 *.jsonl 和 *.json。

Build-CodexChatIndex.ps1 1809 附近：
  增量刷新会根据 size/mtime/detail 文件复用缓存记录。

Build-CodexChatIndex.ps1 6174-6177 附近：
  无论是否有新增或变更，结尾都会重写 html/data/search/cache。
```

### 6.3 判断

刷新变慢不是单纯因为本机 Codex 数据大。

对于 local-claude 和外部 codex_chat 这类小来源：

```text
search/cache 只有 1-5 MB 级别。
如果没有新增记录，理论上应该可以非常快。
V0.18 仍然较慢，主要来自固定的构建流程成本。
```

当前根因判断：

```text
V0.18 的增量刷新已经能复用单个会话解析结果。
但没有“无变化快速返回”。
即使所有文件都未变化，也会继续组装 sessions/appData/search/cache，并固定 ConvertTo-Json + Write-Utf8FileAtomic 重写输出。
local-claude 还会额外读取 Claude sessions 元信息，并递归扫描 projects 下 jsonl/json。
这些步骤在 OneDrive 路径、PowerShell 启动、JSON 序列化和文件写入叠加时，会造成小来源也明显慢。
```

结论：

```text
V0.19 应该优化刷新。
这不是必须接受的性能牺牲。
```

## 7. 刷新性能优化方案

### 7.1 优先目标

优先优化：

```text
刷新过一次后，再次刷新且没有新增/删除/修改记录时，快速完成。
local-claude 和外部 codex_chat 小来源刷新体感明显变快。
local-codex 大来源在无变化时避免重复重写 300MB 级 search/cache。
```

不追求：

```text
本版本不重写整个构建器。
不改变 JSON 输出结构。
不改会话解析结果。
不改变用户主动全量重建的语义。
```

### 7.2 无变化快速返回

在 Incremental 刷新中增加“来源文件签名”判断。

签名建议包含：

```text
sourceId
sourceType
builderVersion
RefreshMode
文件总数
每个源文件的 normalized path
每个源文件的 sizeBytes
每个源文件的 lastWriteTimeUtc
Claude sessions 元信息文件数量、size、mtime
外部来源 root 路径
Claude scan roots
```

如果满足：

```text
当前是 Incremental。
旧 cache 存在且版本兼容。
当前扫描得到的文件签名与旧 cache 中保存的签名一致。
data/search/cache/detail 输出文件都存在。
```

则：

```text
直接返回 summary。
不重写 html。
不重写 data.json。
不重写 search.json。
不重写 cache.json。
不重写 detail。
```

summary 中新增或复用字段：

```text
SkippedWrite = true
NoChange = true
ScannedCount = 当前文件数
ParsedCount = 0
ReusedCount = 当前文件数
ElapsedMs = 实际耗时
Notice = "未发现新增或修改记录，已跳过重写。"
```

### 7.3 输出文件存在性保护

不能只看签名。

即使签名一致，如果以下文件缺失：

```text
CodexChatIndex.data.json
CodexChatIndex.search.json
CodexChatIndex.cache.json
CodexChatIndex.html
```

则不能快速返回，必须执行正常增量构建。

原因：

```text
用户可能手动删除了输出文件。
运行数据可能迁移过。
浏览器需要这些文件存在。
```

### 7.4 detail 文件保护

快速返回前至少检查：

```text
cache 中记录的 detailFileName 对应文件存在。
```

如果 detail 缺失：

```text
不能快速返回。
走正常增量构建或修复缺失 detail。
```

### 7.5 Current 快刷不套用全局快速返回

`RefreshMode=Current` 是“只重新读取当前会话”。

建议：

```text
Current 仍按当前会话路径处理。
如果当前会话文件 size/mtime 未变化，可以只返回当前 detail 不变提示，但不必在 V0.19 强行实现。
V0.19 优先优化普通刷新 Incremental。
```

### 7.6 Full 全量重建不跳过

`RefreshMode=Full` 必须保持：

```text
用户明确要求全量重建时，仍完整扫描、解析、重写。
```

无变化快速返回只适用于：

```text
普通刷新 Incremental。
```

## 9. 副作用与风险

### 9.1 收起后找不到恢复入口

风险：

```text
目录区或标题区彻底消失后，用户可能不知道怎么展开。
```

应对：

```text
在不会随 pane 隐藏的位置显示“展开目录”“展开标题”按钮。
按钮文案明确。
两个区都收起时，两个展开按钮都可见。
```

### 9.2 收起状态持久化可能让下次打开看起来缺栏

风险：

```text
用户上次收起目录/标题，下次打开仍收起，可能误以为界面异常。
```

应对：

```text
展开按钮必须明显。
首次打开默认展开。
只在用户主动点击后持久化。
```

### 9.3 布局变化可能影响小屏幕

风险：

```text
横屏/竖屏下 pane 消失和恢复可能造成宽度计算异常。
```

应对：

```text
使用 CSS class 控制 grid-template-columns。
分别测试：全展开、只收目录、只收标题、全收起。
测试横屏和竖屏。
```

### 9.4 去掉“时间：”降低一点自解释性

风险：

```text
新用户可能不知道最后一个时间是什么。
```

应对：

```text
可见文字去掉“时间：”。
title/aria-label 可保留“生成时间”。
```

### 9.5 搜索按钮组对调影响肌肉记忆

风险：

```text
习惯 V0.18 位置的用户需要适应。
```

应对：

```text
新顺序更贴近语义：搜索范围紧挨搜索框。
按钮文字不变，分组样式不变。
```

### 9.6 无变化快速返回可能漏掉新记录

这是本版本最高风险点。

风险：

```text
如果签名判断过粗，可能误以为没有变化，导致新会话没有进入索引。
```

应对：

```text
不能只比较会话数量。
必须比较每个源文件 path + size + mtime。
Claude 还要把 sessions 元信息文件纳入签名。
签名不一致就走正常增量构建。
输出文件缺失就走正常增量构建。
detail 缺失就走正常增量构建。
```

### 9.7 仍需扫描文件列表

无变化快速返回不等于完全不扫描。

仍需要：

```text
扫描源目录，得到 path/size/mtime。
```

所以：

```text
如果来源目录本身非常大、OneDrive 很慢，仍会有基础扫描成本。
```

但可以避免：

```text
重复解析。
重复组装大对象。
重复 ConvertTo-Json。
重复写入 300MB search/cache。
```

### 9.8 cache 结构升级

需要在 cache 中保存签名。

风险：

```text
V0.18 cacheVersion=2。
V0.19 如果改变 cache 结构，第一次刷新可能无法快速返回，需要正常重建一次。
```

建议：

```text
cacheVersion 升到 3。
第一次 V0.19 刷新正常构建。
第二次起无变化快速返回。
```

这是可接受副作用。
