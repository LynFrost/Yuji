## 5. 问题一：复制按钮点击不应选中提问框

### 5.1 当前问题

用户反馈：

```text
提问框只有点击框内容才会选中。
如果只是点击复制按钮，不要选中。
当前是点击复制按钮也会选中。
```

当前复制按钮由 `renderCopyButton()` 输出，形式大致为：

```html
<button type="button" class="message-copy" onclick="copyMessageText('...')">复制全文</button>
```

当前会话区点击委托会处理提问框选中：

```text
transcript.addEventListener('click', event => {
  如果点击的是 button / a / input / textarea / select，则返回。
  否则选中最近的 data-question-key。
})
```

按当前代码理解，`closest('button')` 理论上应该已经拦截复制按钮点击。如果用户仍然观察到“点击复制按钮也会选中提问框”，说明需要先确认现有拦截在真实浏览器里到底是否生效，不能直接假设就是 `closest('button')` 判断本身失效。

实施前需要用浏览器验收或 DevTools 确认：

```text
点击复制按钮时，event.target 是什么元素。
点击复制按钮时，event.target.closest('button') 是否返回复制按钮。
点击复制按钮时，transcript click 委托是否仍然进入 setSelectedQuestionKey()。
点击复制按钮时，selectedQuestionKey 是否发生变化；如果变化，变化来自哪个调用栈。
```

在根因未完全确认前，V0.26 先采用防御性修复，明确复制按钮和提问框选择之间的事件边界。可能原因包括：

```text
复制按钮自身没有主动 preventDefault / stopPropagation。
外层提问卡片的点击选择逻辑依赖事件委托里的目标判断。
未来如果复制按钮内部增加图标、span 或其他结构，事件目标更容易发生变化。
浏览器焦点与点击顺序也可能让提问框出现选中反馈。
也可能是其他选中路径或焦点路径造成的副作用，需要浏览器验证确认。
```

V0.26 不把这个问题归因于复制文本逻辑本身，而是归因于复制按钮和提问框选择逻辑之间的事件边界不够明确。

### 5.2 推荐方案

采用双层保护：

```text
第一层：复制按钮点击时主动阻止默认行为和事件冒泡。
第二层：transcript 的 click 委托如果发现 event.defaultPrevented，立即返回。
```

不建议把 `copyMessageText()` 做成脆弱的参数重载。

V0.26 建议保持职责分离：

```text
copyMessageText(id)：只负责按 id 复制文本，保留旧接口含义。
handleMessageCopyClick(event, id)：只负责按钮点击事件隔离，然后调用 copyMessageText(id)。
```

新按钮输出建议为：

```html
<button type="button" class="message-copy" onclick="handleMessageCopyClick(event, 'message-copy-1')" title="复制全文">复制全文</button>
```

`handleMessageCopyClick()` 内部规则：

```text
如果 event 存在，先调用 preventDefault()。
如果 event 存在，再调用 stopPropagation()。
然后调用 copyMessageText(id)。
复制成功和失败 toast 仍由 copyMessageText(id) 保持现有行为。
```

`transcript` 点击委托增加防御：

```text
如果 event.defaultPrevented 为 true，直接 return。
再判断 button / a / input / textarea / select 等交互元素。
再执行提问框选中。
```

这样即使后续复制按钮内部结构变化，按钮点击也不会穿透到提问框选中逻辑。

### 5.3 不采用的方案

不建议：

```text
不通过 pointer-events: none 处理复制按钮。
不取消提问框整体点击选中能力。
不把复制按钮移出提问框。
不在复制后强制取消当前选中提问，因为这会破坏键盘上下切换锚点。
```

原因：

```text
用户只要求“点复制按钮不要触发选中”，不是取消提问框选中功能。
复制按钮仍然应该可点击、可键盘访问、可显示 toast。
当前选中提问仍应保持原样，便于后续上下键导航。
```

## 6. 问题二：笔记本横屏向上跳提问框偶发飘动

### 6.1 当前问题

用户反馈：

```text
在笔记本上，横屏使用时，向上跳提问框有时会飘。
台式机连接两个 27 寸屏幕时不会出现。
从上向下跳提问框不会飘。
飘的表现是：跳了之后提问框没有稳定放在当前顶部，右边进度条不是一个方向挪动，而是上下闪。
```

当前键盘跳转链路大致为：

```text
jumpQuestion(direction)
setSelectedQuestionKey(nextQuestionKey, { scroll: true, behavior: 'keyboard' })
scrollToQuestion(selectedQuestionKey, 'keyboard')
scrollTranscriptTo(targetTop, 'auto', element)
```

当前 `keyboard` 跳转使用 `auto`，没有 smooth 动画，这是正确方向。

但当前链路仍有几个不稳定点：

```text
keyboard 跳转没有显式启用 lockTranscriptLayoutForProgrammaticScroll()。
scrollToQuestion() 在同一帧里先设置高亮、再立即测量目标位置，窄视口下布局可能尚未稳定。
content-visibility: auto 会让未进入视口的消息在滚动过程中才完成布局。
calculateQuestionScrollSpacer() 会改变底部 spacer，可能影响 scrollHeight 和最终 scrollTop。
向上跳转会进入更早的、可能尚未完全布局的内容区域，因此比向下跳转更容易出现二次校准。
笔记本横屏可视高度和缩放比例不同，目标元素到顶部的容差更容易暴露。
```

结论：

```text
这更像是“测量时机和布局稳定性”的问题，不像是单纯的 CSS 样式问题。
V0.26 应稳定键盘跳转路径，而不是重写所有滚动逻辑。
```

### 6.2 推荐方案

新增或调整一个专用于键盘上下切换的稳定滚动路径。

核心原则：

```text
仍然使用 auto 滚动，不使用 smooth。
跳转前短暂锁定 transcript 布局，让 content-visibility 临时可见。
锁定后等待一个 requestAnimationFrame，再测量目标位置。
先计算 spacer，再测量目标位置，再执行 scrollTo。
键盘跳转不走长时间收敛循环。
最多做极少量校准，避免出现先上后下的可见闪动。
锁定必须及时释放，避免大型会话滚动性能下降。
```

建议实现路径：

```text
1. jumpQuestion(direction) 仍然只负责计算下一个 questionKey。
2. setSelectedQuestionKey() 在 behavior === 'keyboard' 时调用 stableScrollToQuestionForKeyboard(questionKey)。
3. stableScrollToQuestionForKeyboard() 先 cancelQuestionScrollAnimation()。
4. 调用 lockTranscriptLayoutForProgrammaticScroll(250)，短暂锁定布局。
5. requestAnimationFrame 后查找目标提问元素。
6. 根据目标元素计算 --transcript-scroll-spacer。
7. 再用 getBoundingClientRect() 计算最终 targetTop。
8. transcript.scrollTo({ top: targetTop, behavior: 'auto' })。
9. 下一帧只做一次轻量验证，目标顶部为 16px。
10. 如果 Math.abs(elementTop - 16) <= 6，则认为已经足够稳定，不再修正。
11. 如果 Math.abs(elementTop - 16) > 6，则按同一套测量方式最多做一次 auto 修正。
12. 修正后立即释放锁；无论如何最迟约 250ms 释放锁，不沿用 1200ms 的长锁定。
```

关于 `direction` 参数：

```text
V0.26 不把 direction 作为稳定滚动函数的核心参数。
当前推荐策略是方向无关的：锁定布局、等一帧、测量、auto 滚动、一次阈值验证。
这样可以避免传入 direction 但实际不用，或为了方向差异引入不必要复杂度。
如果浏览器验收后仍确认只有“向上”存在问题，再另立补丁引入方向差异策略。
```

实现上可以采用：

```text
在锁定布局后再进行第一次可见滚动。
键盘跳转不调用 settleUnlockedQuestion() 这种解锁后的长收敛流程。
验证帧只修正超过 6px 的误差，不做 36 帧级别的循环。
6px 以内的偏差保持当前位置，避免为了小误差产生反方向闪动。
超过 6px 的偏差最多修正一次，修正后释放锁，不继续追求数学精确。
setSelectedQuestionKey() 的其他调用方不受影响；只有 behavior === 'keyboard' 走稳定路径。
```

需要同步调整当前布局锁函数：

```text
lockTranscriptLayoutForProgrammaticScroll() 当前有 1200ms 安全超时。
V0.26 建议改为 lockTranscriptLayoutForProgrammaticScroll(timeoutMs)。
timeoutMs 省略时仍默认 1200ms，保持现有非 keyboard 场景行为。
keyboard 稳定跳转传入 250ms，避免大型会话长时间 content-visibility: visible。
unlockTranscriptLayoutForProgrammaticScroll() 保持现有职责。
```

### 6.3 为什么不扩大为全局滚动重构

不建议 V0.26 重写所有滚动逻辑。

原因：

```text
当前只反馈了“笔记本横屏向上切提问偶发飘”。
回到顶部、切换会话、刷新保持进度、搜索恢复锚点等功能已经依赖现有滚动逻辑。
全局重构容易引入新的定位偏差。
大型会话对滚动性能非常敏感，不能因为修一个偶发问题让整体滚动变卡。
```

因此 V0.26 只对键盘提问跳转路径做稳定化。

## 8. 副作用与规避

### 8.1 复制按钮事件隔离过强

副作用：

```text
如果 stopPropagation 用得过宽，可能影响按钮周边的焦点行为或统计逻辑。
```

规避：

```text
只在复制按钮自己的点击事件里 preventDefault / stopPropagation。
不要阻止整个提问框的点击事件。
不要阻止键盘上下键事件。
```

### 8.2 复制按钮键盘可访问性下降

副作用：

```text
如果只处理鼠标点击，键盘 Enter / Space 激活按钮可能出现行为不一致。
```

规避：

```text
保留 button type="button"。
按钮点击入口使用 handleMessageCopyClick(event, id)，可覆盖鼠标和键盘激活。
copyMessageText(id) 保持复制职责，不承担事件判断。
不要把按钮改成 div。
```

### 8.3 当前选中提问保持不变可能让用户误解

副作用：

```text
用户点击某个未选中提问里的复制按钮后，选中状态不会切到该提问。
```

规避：

```text
这是本次需求的目标行为。
复制按钮只负责复制，不负责改变阅读锚点。
如果用户想选中该提问，应点击提问正文区域。
```

### 8.4 键盘跳转多等一帧

副作用：

```text
为等待布局稳定，键盘跳转可能增加约一帧延迟。
```

规避：

```text
只对 keyboard 跳转使用该稳定路径。
使用 auto 滚动，不使用 smooth。
不做长时间收敛循环。
只等待一个 requestAnimationFrame 后测量。
目标是减少可见闪动，而不是增加动画。
```

### 8.5 临时显示 content-visibility 内容带来性能成本

副作用：

```text
layout lock 会让 .message 和 .collapsed-group 临时 content-visibility: visible。
大型会话中，如果锁定时间过长，会增加布局和内存压力。
```

规避：

```text
键盘跳转锁定时间控制在很短范围内，建议约 250ms。
lockTranscriptLayoutForProgrammaticScroll(timeoutMs) 保留默认 1200ms，避免影响已有非 keyboard 场景。
跳转完成后立即释放。
不要在普通滚轮滚动期间启用该锁。
不要为每个提问永久取消 content-visibility。
```

### 8.6 过度抑制反向修正导致目标没有完全贴顶

副作用：

```text
如果为了避免闪动完全禁止修正，极端布局变化下目标提问可能离顶部有少量偏差。
```

规避：

```text
先通过锁定布局和延后一帧测量减少偏差来源。
以目标顶部 16px 为准。
偏差 <= 6px 时保持当前位置，不修正。
偏差 > 6px 时允许一次 auto 修正。
不做肉眼可见的来回多次修正。
验收标准是稳定放到顶部附近，而不是数学上每次都正好 16px。
```

### 8.7 笔记本问题可能与缩放比例有关

副作用：

```text
如果问题和浏览器缩放、系统 DPI、窗口高度有关，单一尺寸验收可能复现不充分。
```

规避：

```text
至少用一个笔记本横屏近似尺寸验收。
如条件允许，再用 100% 和 125% 缩放分别观察。
方案应依赖 DOM 实测位置，不写死屏幕尺寸。
```

### 8.8 归档副本带来入口混淆

副作用：

```text
软件/CodexChatIndex_V0.25 和 软件/CodexChatIndex 会同时存在。
如果误打开 CodexChatIndex_V0.25/Open-CodexChatIndex.cmd，可能运行旧版本。
```

规避：

```text
明确当前入口始终是 软件/CodexChatIndex/Open-CodexChatIndex.cmd。
CodexChatIndex_V0.25 只作为回滚归档。
```

### 8.9 demo-55-6-push.txt 被误复制或误改

副作用：

```text
demo-55-6-push.txt 虽位于源码目录，但用户明确要求不归档、不改动。
如果按 git ls-files 全量复制，会误把它复制进 CodexChatIndex_V0.25。
```

规避：

```text
归档复制必须按第 3.1 节白名单执行。
不要使用未过滤的 git ls-files 全量复制。
实施后检查 CodexChatIndex_V0.25 中不存在 demo-55-6-push.txt。
```
