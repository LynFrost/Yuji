# V0.37：Codex 子会话历史备注关联兼容修复

## 1. 基本信息

- 仓库：`LynFrost/Yuji`（语迹）
- 目标分支：`feature/v0.37`
- 文档性质：问题诊断、修复需求、实现建议与验收标准
- 当前任务边界：**只提交此需求文档，不修改、测试或执行程序源码；不得改写用户本地备注文件**。
- 上游基础：V0.35 继承树与 V0.35.2 压缩会话支持；保留 V0.36 的大标题元信息恢复功能。

## 2. 故障现象与已验证证据

用户升级后，语迹的子会话备注标记、悬停或常驻备注大量不可见，但访问本地接口 `GET /api/notes?sourceId=local-codex` 仍能返回备注记录。

用户通过浏览器开发者工具执行**只读**检查，得到：

| 检查项 | 结果 |
| --- | ---: |
| 接口返回的键数量（首次检查） | 139 |
| 当前页面 `.session-btn` 子会话节点数 | 120 |
| 使用当前 DOM 备注键直接匹配且有备注正文的节点数 | 0 |
| DOM 带 `has-note` 标记的子会话节点数 | 0 |
| 第二次检查中过滤出的 `session` 类型备注项数 | 123 |
| 旧备注路径与当前节点路径完全一致的节点数 | 0 |
| 仅相差末尾 `.zst` 的节点数 | 47 |
| 会话 ID 能在备注中匹配的节点数 | 47 |
| 当前以 `.jsonl.zst` 结尾的节点数 | 120 |

**解释边界**：
- “接口返回 139 个键”不等于 139 条去重后的原始备注；服务端有历史键别名兼容逻辑。
- “47 个仅 `.zst` 后缀不同”和“47 个 ID 匹配”是分别计算的计数，尚未确认这两组完全相同。
- 另外 73 个页面节点未匹配到对应旧路径，不代表这些节点原先都添加过备注。
- 已证实至少存在**旧路径与压缩路径不一致造成匹配失败**的案例；是否还有独立的旧 `group` 备注失配、其他路径迁移或刷新问题，需要分别验证。
- 接口能返回备注说明备注没有整体消失；但仅凭接口截图不应承诺所有历史备注完整无损。

## 3. 成因与提交回溯

### 3.1 压缩文件后缀引起键失配（已得到数据支持）

当前 `templates/CodexChatIndex.template.html` 的 `createSessionNoteTarget()` 生成备注键时：

```javascript
const identity = (session && (session.path || session.key || session.id)) || '';
const key = 'session:' + sourceId + ':' + stableHash(identity);
```

旧备注按照物理路径 `.../rollout-xxx.jsonl` 生成键；Codex 压缩文件在索引中以 `.../rollout-xxx.jsonl.zst` 呈现时，`stableHash(identity)` 改变，原有 `session` 键无法命中。

相关提交：`71aff58fe0279a000b48b2963b7fea011a360ebf`（V0.35.2，支持压缩 Codex 文件）。该提交让解析与缓存回退能够兼容压缩文件，**却没有同步解决备注键对物理路径变化的依赖**。它不是删除备注的提交；根本隐患是更早的“以完整文件路径作为备注身份”设计。

### 3.2 继承树改变原标题分组（需覆盖兼容验证）

`dfb5298ef63d5ef3b12e26884879286601ef6fb5`（V0.35，引入真实继承树）使部分原本独立的单会话大标题变为其他标题下的子会话节点。

原单会话大标题的备注可能按：
`group:<sourceId>:<workspaceHash>:<titleHash>`
保存；新树中子会话节点默认只查询：
`session:<sourceId>:<pathHash>`。

现有 `applyNoteMetadata()` 仅按当前目标键直接 `getNote(target.key)`，因此当节点身份从旧标题组变为新会话节点时，旧 `group` 备注可能不可见。**这属于代码逻辑可推导的兼容风险，不能仅凭前述 47 条数据认定所有 `group` 备注均受影响。**

### 3.3 备注后端未发生上述版本间的删除逻辑变化

回溯中 V0.34、V0.35 和 V0.36 的 `CodexChatIndexServer.py` 内容 SHA 相同，备注文件仍为运行数据目录下的 `CodexChatIndex.notes.json`。本次修复应优先采用非破坏性读取兼容，而非清空、重建或批量重写历史备注。

## 4. 必须满足的修复需求

### 4.1 session 备注：兼容 `.jsonl` 与 `.jsonl.zst`

1. 优先使用当前会话计算的原有 `session` 键匹配；现有键命中时不得被历史回退覆盖。
2. 若当前路径以 `.jsonl.zst` 结尾且未命中，使用**仅移除末尾 `.zst`** 后的路径，按原有 `stableHash` 规则计算旧键并尝试匹配。
3. 反方向 `.jsonl` → `.jsonl.zst` 的路径切换可对称兼容，但必须使用严格后缀判断；不能对路径任意位置进行宽泛替换。
4. 保留原路径的大小写、分隔符和字符串规则，不要为了兼容擅自改变旧键的哈希算法输入；可另外用标准化路径做候选关系核验，不可取代原样计算旧键。
5. 应同时利用备注内已有的 `sessionId`、`path`、`sourceId` 信息验证回退候选的归属；**发现多条冲突候选时不自动绑定、覆盖或迁移**，应保留可诊断信息。
6. 正常保存的当前版本 `session` 备注不得因兼容旧路径而消失、重复展示、错误覆盖或匹配到其他会话。
7. 历史备注恢复后，标记点、悬停浮层、常驻浮层、右键编辑/删除均应正确使用**实际命中的备注**；不能只修复文字展示而继续让编辑界面把它当成“新建备注”。

### 4.2 group 备注：兼容原独立标题变成子会话节点

1. 识别 V0.34 及之前按标题组保存的旧 `group` 备注。
2. 旧 `group` 备注的原含义是**工作目录 + 标题组**，不能不加区分地复制给新继承树内所有同名子会话。
3. 仅当源、工作目录、旧标题以及原始会话归属能唯一、可靠确认时，允许以兼容视图将该旧备注关联到恰当节点；其他情况不得猜测。
4. 如旧组实际上包含多个会话，或同名标题在多处出现且缺少唯一归属证据，保留旧备注并提供可诊断/可人工识别的回退方案，不要自动转为某个 `session` 备注。
5. 新旧 `group` / `session` 键同时存在时，明确优先级与冲突处理规则，禁止静默覆盖原有用户内容。
6. 显示、编辑、删除应一致地引用真实备注目标；不得因从 `group` 回退显示，就用错误的 `session` 键修改或删除原记录。

### 4.3 用户数据安全与写入规则

1. 修复前应提示用户备份 `运行数据/CodexChatIndex.notes.json`，并保证首次升级和索引重建不会清除备注。
2. **本版本默认不批量迁移、不覆盖、不删除历史备注**；优先只读兼容旧键。
3. 如果后续决定将备注主键迁移到稳定 `sessionId`，须作为独立、可回滚的迁移方案设计，并处理来源隔离、ID 冲突、旧键、同步数据及编辑兼容，不能本次直接替换 `stableHash(path)`。
4. 禁止用户仅因备注不可见就需要重新手工创建相同备注。
5. 不修改 Codex 原始 `.jsonl` / `.jsonl.zst` 聊天记录。

## 5. 实现建议（供开发参考，非本次执行）

- 优先在 HTML 模板的备注定位层引入统一的历史备注解析器，而不是在不同渲染、浮层、菜单里各实现一套不一致的回退。
- 解析结果建议明确携带 `note`、`matchedKey`、`matchedType`、`matchReason`、`ambiguous` 等信息，以供展示与写入行为一致使用。
- `createSessionNoteTarget()` 与 `createGroupNoteTarget()` 可保留现有主键算法；由解析器按有序候选查找当前键、严格后缀兼容键及有条件的旧标题组键。
- 检查 `applyNoteMetadata()`、`getNote()`、`showNoteTooltip()`、`refreshPinnedNotes()`、`openNoteMenu()`、保存及删除入口：同一节点必须具有一致的有效目标身份，不能发生“显示的是旧备注、编辑/删除的却是新键”的分裂。
- 服务端已有 `normalize_notes_payload()` 的 source-scoped 别名处理；新增兼容不得破坏老版本别名逻辑和 `sourceId` 隔离。
- 不应顺带调整继承树结构、标题单行/大标题元信息或其他无关功能。

### 6.2 结合本机故障的验收

- 使用备份后的原始备注文件在可控测试环境复现问题，不应直接修改用户原件。
- 原先控制台显示的 `当前120个子会话／成功匹配0／已标记0`，修复后应至少恢复那批**可唯一确定归属且仅差末尾 `.zst`** 的旧备注；具体可恢复数量以去重并逐条核对后的结果为准，不武断要求 120 条全部有备注。
- 对旧 `group` 备注单独列出“唯一匹配／歧义待处理／无法确认”的数量，不把它与压缩路径的 47 个计数混为一谈。
- 修改前后对备注 JSON 进行去重记录数量与内容完整性校验；在未执行用户主动编辑/删除操作的情况下，不应减少或覆盖原备注。
- CI 增加适用的后端/前端回归覆盖；仅检查 DOM 类名或测试正则匹配不足以证明真实备注可恢复，需包含带旧键样本的行为测试。

## 7. 非目标与实施边界

- 不将 139、123 或 47 视为需要创建/迁移的固定备注数量。
- 不改变备注文案、聊天内容、文件压缩状态或界面设计。
- 不将“所有备注消失”当作后端数据已丢失的既定事实。
- 本文档仅确认需求和建议修复路线；**编写和提交本文档不代表代码修复、CI 执行或本机验证已经完成**。
