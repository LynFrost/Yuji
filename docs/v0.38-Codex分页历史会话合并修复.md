## 2. 问题现象

语迹展示一条很长的 Codex 对话时，列表标题与详情内容从对话中间开始，较早的消息没有出现在网页中。

对照 Codex 原生界面与语迹页面，可观察到：

1. Codex 原生界面显示的是一条从 2026-09-29 开始、持续到 2026-10-01 的长会话，包含更早的讨论、开发阶段记录和后续追问。
2. 语迹列表却将 2026-10-01 10:06 左右的一条中途用户消息当作会话标题。
3. 选中该列表项后，详情也从这条中途消息开始，之前已经存在于 Codex 原始历史中的消息没有显示。
4. 用户提供的五个原始 `.jsonl.zst` 文件均可找到，说明至少本案例的早期历史文件仍存在于本机；当前现象不能简单归因为原始会话文件已被删除。

**问题性质：会话历史在语迹的索引/详情模型中被分段展示，逻辑会话的完整历史没有被正确重组。不是单纯的 CSS、卡片高度或滚动位置问题。**

## 3. 已检查的原始证据

### 3.1 五个物理文件属于同一条逻辑历史链

本案例涉及以下文件（省略共同的本机目录前缀）：

| 顺序 | 文件名时间 | 文件名中的分段标识 |
| --- | --- | --- |
| 1 | 2026-09-29 10:13:39 | `01a0eaf0-6873-70d2-8be6-ee1d13043092` |
| 2 | 2026-09-29 20:28:34 | `01a0ed23-64f8-7632-84bf-d8c829c2dd9b` |
| 3 | 2026-09-30 09:33:15 | `01a0eff1-ca46-7491-9689-b6d6d9352f7a` |
| 4 | 2026-10-01 09:37:39 | `01a0f51c-2dee-78e3-9e05-eb0f12106c36` |
| 5 | 2026-10-01 10:06:24 | `01a0f536-7eec-7fb3-a399-d73bc7f6b7e1` |

对五个文件的内部记录检查得到：

- 五个文件的 `session_meta.id` 相同：`01a0eaf0-6873-70d2-8be6-ee1d13043092`。
- 五个文件的 `history_mode` 均为 `paginated`。
- 五个文件的 `context_window.window_id` 相同。
- 后续文件的 `history_base.thread_id` 与前一段的历史标识形成连续引用链。
- 文件时间顺序与内部历史链顺序相吻合。

因此，本案例不是五个无关的会话恰好标题相似，而是**同一个逻辑会话的分页历史被保存为多个物理 rollout 文件**。构建器必须利用文件内的关系元数据识别分页链，不能仅依据文件数量、时间接近或标题相似来判断。

### 3.2 消息数量只能作为原始记录统计

本次只读统计得到五个文件中非空用户消息记录数分别为 96、19、80、5、94，合计 294 条原始用户消息记录。

这些数值是按物理文件统计的记录数，**不是去重后的逻辑会话消息总数**。由于分页边界可能存在重叠或重复记录，实施时必须依据稳定的记录标识和分页关系处理重复，不得把 294 直接作为验收时的最终消息数量。

### 3.3 正式标题应来自会话元数据

本机 `C:\Users\Administrator\.codex\session_index.jsonl` 中，该会话 ID 对应的 `thread_name` 为“规划3D探针测试与交付流程”。本机 Codex 状态数据库中也存在对应会话元数据。

原始分页文件的 `session_meta` 本身不包含这个正式显示名称。因此，语迹不应把每个分页文件中的第一条用户消息当作整个逻辑会话的标题。应优先读取 Codex 可用的正式会话名称，并保留兼容回退。

## 4. 根因分析

### 4.1 索引构建器按物理文件独立生成会话

当前 `Build-CodexChatIndex.ps1` 的相关流程包括：

- `Read-CodexSession` 逐个解析物理会话文件。
- 构建流程遍历文件，并将解析结果逐个加入会话列表。
- 标题生成逻辑从当前文件解析到的用户消息中取第一条作为标题候选。
- 文件名后缀处理会回退读取 `session_meta.id`，因此多个物理文件可以得到相同的逻辑会话 ID；但 ID 相同并不意味着消息已经合并。

这使得同一逻辑会话的每个分页文件都可能独立生成一条列表记录，并各自使用本段的第一条用户消息作为标题。

### 4.2 前端仍然以物理路径区分详情

当前 `templates/CodexChatIndex.template.html` 存在以下相关行为：

- `getSessionKey()` 优先使用 `session.key`、`session.path`，最后才使用 `session.id`。
- 继承关系注册表发现重复 ID 时，会将歧义 ID 从可确认的父子关系注册表中排除。
- 详情匹配优先比较物理文件路径；路径不同的分页文件仍会被当作不同详情。
- 因此，即使多条记录具有相同的 `session_meta.id`，前端也仍可能分别加载单个文件的详情，而不会自动补齐其他分页文件。

这解释了为何列表标题和详情正文会同时从中途开始。仅调整标题生成或 UI 样式不能修复完整历史缺失。

### 4.3 需要区分的两类问题

本次主要修复的是**分页历史的逻辑会话识别与完整详情组装**。正式标题读取是同一问题中的相关需求，但应单独验收。

当前证据支持“语迹没有把这五段分页历史重组成一条完整逻辑会话”；不应据此推断所有 Codex 会话都采用相同分页方式，也不应把所有同 ID 文件无条件合并。

## 5. 修复目标

1. 将属于同一条分页历史链的多个物理文件识别为一个逻辑会话。
2. 通过 `session_meta.id`、`history_mode`、`context_window.window_id`、`history_base.thread_id` 等内部元数据建立关系；时间和文件名只能用于辅助核验，不能替代明确的关系证据。
3. 将各段的消息与事件按真实历史顺序组装成完整详情，保证早期消息不会因选中较新的分页文件而被遗漏。
4. 只生成一个逻辑会话列表项，使用最早有效历史与正式会话元数据计算标题、创建时间、摘要和消息数量；更新时间取整条逻辑会话最新的有效时间。
5. 兼容普通 `.jsonl` 与压缩 `.jsonl.zst` 文件，不修改原始文件、不要求用户手工解压。
6. 保留 V0.35.2 压缩文件读取、V0.36 大标题元信息、V0.37 备注兼容，以及现有搜索、筛选、排序、图片、工具事件和来源隔离行为。
7. 对无法确认的历史链、缺失分段、分叉或重复记录采取保守策略，并提供可诊断信息；不得静默拼接可能无关的对话。

## 6. 实现要求与建议

### 6.1 在索引阶段建立“逻辑会话—物理分段”模型

建议在现有会话数据结构中增加明确的分页分段信息，而不是只把多个文件的路径简单拼成一个字符串。可考虑以下逻辑字段（字段名为设计建议，实施前应与当前数据结构核对）：

- `logicalSessionId`：逻辑会话稳定 ID。
- `segments`：该逻辑会话包含的物理分段列表。
- `segmentPath` / `path`：每个分段的原始路径。
- `segmentOrder`：由分页引用关系推导的顺序。
- `historyMode`、`windowId`、`historyBaseThreadId`：用于诊断与验证关系的元数据。
- `relationStatus`：例如 confirmed、incomplete、ambiguous；具体枚举需与现有代码风格统一。

约束：

1. 只有关系证据充分且链条唯一时，才将多个文件合并为同一逻辑会话。
2. 不应仅因 `session_meta.id` 相同就无条件合并；需检查分页模式、窗口标识和历史基引用。
3. 对缺少前段的链，可展示已确认的可用内容并标明历史不完整；不得把缺失内容伪装成已完整加载。
4. 对分叉、循环、重复引用或多条候选前段，不自动猜测连接顺序；应保留独立记录或标记歧义并输出诊断。
5. 普通非分页会话继续沿用原有路径，不应被新逻辑意外合并。

### 6.2 正确组装消息与处理分页重叠

- 按 `history_base` 的真实引用关系确定分段顺序，不单纯按文件修改时间排序。
- 每个分段仍使用现有 JSONL / Zstandard 解压与事件标准化流程。
- 若记录有稳定的事件 ID 或消息 ID，应优先使用这些标识识别分页重叠。
- 不得只按消息正文去重：用户可能合法地重复发送相同文本。
- 如果某类分页记录没有可靠的唯一标识，应依据已验证的分页边界规则处理；无法安全去重时保留记录并记录诊断，不得任意丢弃。
- 维持 user、assistant、tool、system 等事件的先后关系，以及图片、工具调用、工具输出和消息关联。
- 摘要、首条有效用户提问、创建/更新时间和事件计数应以组装后的逻辑会话计算，不能继续只取当前物理分段的数据。
- 读取某一分段失败时，不应把整个逻辑会话静默变成空会话，也不应在索引更新中误删其余有效分段。

### 6.3 详情加载与前端身份

- 列表中的一个逻辑会话应能请求并显示全部已确认分段的详情。
- 详情接口/缓存需要使用稳定的逻辑会话身份，同时保留物理分段路径用于读取源文件、诊断与增量更新。
- 不能仅通过 `session.id` 在重复 ID 的物理文件中任选一个详情；必须明确选择逻辑会话聚合详情。
- 如果现有架构仍采用“每个物理文件一份详情 JSON”，可以在索引层建立分段清单，并在详情读取层按清单顺序组合；不要求为实现而大规模重写后端。
- 分段文件新增、更新、压缩状态改变或消失时，应重新计算对应逻辑会话的分段关系和缓存指纹，避免旧缓存继续显示不完整历史。
- 详情加载过程中应保持当前选择状态，不能因异步请求先后导致旧分段覆盖完整聚合结果。

### 6.4 标题与元数据

优先级建议：

1. 使用 Codex 元数据中与逻辑会话 ID 对应的正式名称（例如可用的 `session_index.jsonl` 的 `thread_name`，或经核实可用的状态数据库字段）。
2. 正式名称缺失时，使用最早已确认分段中第一条真实、有效的用户提问作为回退。
3. 不将分页文件后续分段的第一条用户消息用作整个会话标题。
4. 不把 Codex 内部控制标记、工具事件、空消息或仅有附件元数据的记录误作标题。
5. 标题来源不可用时使用现有的未命名回退，并保留诊断信息；不得因元数据读取失败导致会话详情丢失。

正式名称的读取应复用项目已存在的数据来源；如果需要新增数据库读取或新的外部依赖，必须先核对部署环境和数据兼容性，避免为本次修复引入不必要的依赖。

### 6.5 备注与既有用户数据保护

合并分页会话可能改变列表项身份或详情路径，因此必须明确保护 V0.37 已修复的备注兼容：

- 不删除、不重写、不批量迁移备注 JSON。
- 保留旧的物理分段路径和原有备注键，确保升级后已有备注仍能找到。
- 如果不同分段各自有备注，不得在合并时静默覆盖或合并正文；应保留各自记录，并按既定规则显示、编辑和删除。
- 不得出现“显示的是分段 A 的备注，点击编辑/删除却操作分段 B 或新建键”的情况。
- 对旧键、当前键或多个分段备注存在冲突时，遵循 V0.37 的唯一匹配、歧义保护和只读兼容原则。
- 备注匹配、会话隐藏状态、固定/排序偏好和来源隔离必须纳入回归测试。

### 6.6 缓存、增量与性能

- 将分页关系元数据和分段路径纳入逻辑会话缓存的有效性判断。
- 任一分段内容、修改时间、大小、分段关系或压缩状态发生变化时，应让对应逻辑会话的聚合详情失效并重建。
- 全量刷新和增量刷新必须共用一致的分页识别规则。
- 避免每次页面渲染都重新解压所有历史文件；应在索引/详情构建阶段复用已有缓存策略。
- 对大体积 `.jsonl.zst` 继续使用项目已有的安全读取路径，不永久写出解压副本。
- 单个文件损坏、被截断或暂时无法读取时，保留可用的旧索引/详情，并提供可定位的诊断；不得将读取失败直接解释为该会话已删除。

- 不重做 Codex 普通 `.jsonl` / `.jsonl.zst` 的基础解压能力。

- 不改写 Codex 原始历史文件、用户备注文件或本地用户配置。
- 不把本次任务扩大为所有历史数据的批量迁移。

如果只读核查发现必须扩大范围，应先列出原因、文件、风险和替代方案，待用户确认后再实施。

### 验收时的证据要求

- 使用用户提供的五个脱敏/受控样本，或由它们提炼出的合成样本进行复现；不要将真实会话内容提交进仓库。
- 记录聚合前后物理文件数、逻辑会话数、事件数及去重数；明确这些统计的定义。
- 对比聚合后的首条有效用户消息、末条有效事件、标题、创建/更新时间和消息顺序。
- 对照 Codex 原生界面确认早期历史已恢复，不以“列表只有一项”作为唯一通过标准。
- 对备注和其他用户数据执行前后完整性检查。
