## 2. 问题现象

当前 V0.38 在真实 Codex 分页历史中仍有两个相互关联的问题：

1. 同一条长会话被拆成多个列表项。列表标题可能取自中间某个分页文件的首条用户消息，选中后右侧详情也只加载该物理文件，较早的历史没有出现在同一详情中。
2. 一个分页文件末尾的用户提问没有显示回答，而紧接着的后续分页文件开头出现一条相同或高度相似的提问，回答位于后续分段。由于当前页面只加载单个物理分段，用户会看到“提问没有回答”。

当前复现样本横跨 2026-09-29 至 2026-10-01，涉及五个物理 rollout 文件。样本的逻辑会话 ID、分页模式和窗口 ID 相同，文件内部的历史基引用指向连续的分页关系，但索引中仍出现多条 `paginationStatus = ambiguous` 的记录。

本次修复的目标是恢复**一个逻辑会话、一个完整的有序详情、正确的问答关联**，而不只是改变标题或页面布局。

> 实施和测试必须使用合成样本，不要把真实会话正文、真实会话 ID、用户目录或私有对话内容写入仓库。

## 3. 已定位的根因

### 3.1 复合文件名导致物理分段 ID 被覆盖

主要检查位置：`Build-CodexChatIndex.ps1` 中的 `Read-CodexSession`，以及 `scripts/CodexSessionCompatibility.ps1` 中的文件名处理辅助函数。

真实分页文件名有两种结构：

- 根分段：`rollout-<时间戳>-<logical-session-id>.jsonl` 或 `.jsonl.zst`
- 后续分段：`rollout-<时间戳>-<logical-session-id>_<physical-segment-id>.jsonl` 或 `.jsonl.zst`

当前解析流程先剥离时间戳前缀，再将剩余部分作为候选 `Id`。`<logical-session-id>_<physical-segment-id>` 不是单个 UUID，因此不能通过现有的单 UUID 检查。随后，解析器会允许 `session_meta.payload.id` 覆盖候选 `Id`。结果是多个物理分段都可能使用同一个逻辑会话 ID 作为 `Id`。

分页合并器则需要使用每个物理分段自己的 ID，才能把 `history_base.thread_id` 解析到唯一的前一分段。多个分段 ID 被覆盖成同一个值后，引用关系出现重复候选，链条被判定为歧义，合并器便保留了各个物理文件。

### 3.2 当前测试夹具没有复现真实命名格式

V0.38 的分页测试使用了简化的分段文件名：测试中的后续分段只使用单独的物理分段 ID，没有覆盖真实的 `<logical-session-id>_<physical-segment-id>` 结构。

因此，测试能够通过并不代表真实 Codex 文件名能够正确解析。V0.39 必须修正测试夹具，让文件名、`session_meta.id` 和 `history_base.thread_id` 的组合与真实格式一致。

### 3.3 现有稳定 ID 去重不能解决跨分段重复提问

当前聚合逻辑主要按 `kind + stableItemId` 去重。分页边界的两条相同或近似提问可能拥有不同的 `stableItemId`，因此会保留为两条消息。

真实样本中，前一段末尾和后一段开头的两条提问非常接近，但并非完全相同。不能简单地假设正文完全相等，也不能在整个会话中按文本相似度全局去重。否则可能误删用户确实重复提出的问题。

### 3.4 详情渲染依赖有序事件流

模板中的 `buildReaderMarkup` 会在遇到用户消息时更新当前问题，并将后续助手最终回答关联到当前问题。因此，若分页文件未合并，后续回答自然不会出现在前一段的详情里；若合并时没有先处理已确认的边界重复提问，页面也可能显示一条无回答的提问，随后又显示一条相似提问及其回答。

应优先修复索引层的分段身份、链条和事件聚合。只有在回归测试证明现有前端关联逻辑仍无法正确展示聚合结果时，才修改模板。

## 4. V0.39 修复目标

1. 分离并正确维护逻辑会话 ID 与物理分段 ID。
2. 按真实分页引用关系合并所有可确认的分段，形成唯一的逻辑会话列表项。
3. 正确排序、聚合详情事件，保留工具调用、工具输出、系统事件、图片引用和消息顺序。
4. 只在严格的分页边界条件满足时，处理跨分段重复或近似重复的未回答提问；不做全局模糊去重。
5. 让后续分段中的助手回答能够关联到保留的提问。
6. 通过缓存版本/解析器版本更新，避免旧缓存继续显示错误的分段结果。
7. 将产品显示版本与构建器版本更新为 `V0.39`，保留旧版本文档与历史记录。
8. 保持普通非分页 Codex 会话、Claude 等其他来源、备注、隐藏状态、排序和来源隔离行为不变。

## 5. 实现要求

### 5.1 明确区分逻辑会话 ID 和物理分段 ID

建议在现有文件兼容辅助代码中新增一个明确的文件身份解析函数，或以等效的可测试方式实现。不要再让同一个字符串同时承担逻辑会话身份与物理分段身份两种职责。

解析规则：

1. 先按现有兼容规则移除 `.jsonl` / `.jsonl.zst` 后缀及 `rollout-<时间戳>-` 前缀。
2. 若剩余部分是单个 UUID，它是根分段的文件身份；该分段的物理 ID 可等于逻辑会话 ID。
3. 若剩余部分符合 `<logical-session-id>_<physical-segment-id>`，分别解析前后两个 UUID：前者是文件名中的逻辑会话 ID，后者是物理分段 ID。
4. `session_meta.payload.id` 仍作为逻辑会话 ID 的权威候选；若它与文件名中的逻辑 ID 冲突，应标记元数据歧义并输出诊断，不可静默覆盖物理分段 ID。
5. 对分页会话，`Id` 必须保留为物理分段 ID；`LogicalSessionId` 才表示逻辑会话 ID。
6. 对普通非分页会话维持原有身份规则，不能因为新增复合文件名解析而改变其列表身份。
7. 对不符合已知格式、UUID 缺失或格式冲突的文件采取保守降级，保留可用原始记录并标记诊断，不得猜测 ID 或把多个文件错误合并。

必须为根分段和后续分段分别增加测试，并断言：同一逻辑会话的多个物理分段拥有相同的 `LogicalSessionId`、不同且正确的 `Id`。

### 5.2 使用物理分段 ID 建立唯一历史链

- 以逻辑会话 ID、窗口 ID、工作目录及分页模式等现有元数据作为分组条件。
- 用物理分段 ID 建立 ID 查找表，再通过 `history_base.thread_id` 查找唯一父分段。
- 按引用关系生成链条顺序，不能仅按文件时间或目录枚举顺序排序。
- 只有当链条的根、父子关系、分叉/循环检查和分段覆盖情况满足现有安全条件时，才标记为完整确认的聚合会话。
- 对父分段缺失、ID 重复、窗口不一致、分叉、循环、元数据冲突等情况，保留独立记录或标记 `incomplete` / `ambiguous`，同时给出可定位的诊断。
- 不得仅因 `session_meta.id` 相同就无条件合并，也不得因标题相同、时间接近或消息正文相似而合并独立会话。
- 同一逻辑会话成功合并后，列表中只保留一个逻辑会话项，并记录有序的物理分段清单，以便详情读取、缓存失效和备注兼容继续定位到各源文件。

### 5.3 聚合事件与分页边界重复提问处理

先保留现有稳定事件 ID 去重，再增加一个**只作用于相邻、已确认分页分段边界**的重复提问识别步骤。不得对整条会话执行无条件的文本去重。

边界候选必须同时满足以下结构条件：

1. 两个分段属于同一条已确认的连续分页链，并且是直接相邻分段。
2. 前一分段末尾的最后一条有效对话事件是用户提问；在该分段结束前，没有属于该提问的助手最终回答。
3. 后一分段开头的第一条有效对话事件也是用户提问；其前面只能有允许忽略的任务开始等非对话控制记录，不能有其他用户或助手对话。
4. 两条提问时间间隔不超过 60 秒。
5. 两条提问的规范化文本完全相同，或在较长文本中仅存在一个字符级编辑差异。文本规范化仅允许去除首尾空白、统一换行并折叠连续空白；不能删除语义字符、任意标点或用户输入内容。
6. 两条消息的稳定事件 ID 不同，且没有其他更可靠的记录关系可用于判定它们是两个独立问题。

处理规则：

- 对满足全部条件的高置信边界重复，保留前一分段的提问作为展示中的规范事件，抑制后一分段重复的提问事件，并将后一分段紧接着的回答接到该规范提问之后。
- 必须在聚合后的详情/索引数据中保留可诊断的来源映射，例如记录被抑制事件的源分段、原始事件 ID 以及其归并目标；不能修改或删除 Codex 原始文件。
- 对较短文本、编辑差异超过一个字符、间隔超限、存在中间对话事件或任何关系不确定的情况，不自动删除消息；保留两条记录并输出可诊断信息。
- 不得仅凭“内容看起来相似”就跨越多个分段、跨越其他对话事件或全局去重。
- 对边界处理前后分别统计原始事件数、稳定 ID 去重数、边界归并数和最终展示事件数，避免把去重前后的不同口径混为一谈。

上述规则是为当前边界问题设置的保守策略。若合成测试显示单字符差异规则仍会误合并独立提问，应进一步收紧规则；不能为了让一个样本通过而牺牲一般消息完整性。

### 5.4 保证助手回答与规范提问关联

- 事件聚合完成后，按时间和已确认的分段顺序生成连续事件流。
- 若边界重复被归并，必须在生成问题键/回答关联前完成归并，确保后续 `assistant_final` 关联到保留的规范提问。
- 保留事件的来源路径、时间戳、稳定 ID 和 turn 相关信息，便于诊断与追溯。
- 对普通独立提问，即使正文与前一条消息相同，也必须保留各自的问答关联。
- 检查模板中的 `buildReaderMarkup`、`questionKey` 与回答渲染逻辑。若现有逻辑在接收到正确的聚合事件流后即可正确配对，则不修改模板；只有测试证明仍有问题时才做最小修正。
- 不通过前端隐藏某条消息来掩盖索引层分段错误；列表身份、详情数据与事件计数必须来自同一聚合模型。

### 5.5 标题、时间和统计信息

聚合后，以下字段必须基于逻辑会话计算，而不是只使用当前物理分段：

- 标题：优先采用可用的 Codex 正式会话名称；缺失时回退到最早已确认分段中的第一条真实有效用户提问。
- 创建时间：取最早已确认分段的有效创建时间。
- 更新时间：取所有已聚合分段中最新的有效更新时间。
- 摘要：从最早的有效历史生成。
- 用户数、助手数、消息数：以聚合和去重后的事件为口径，并在测试中明确统计规则。
- 分段数、原始事件数、去重数和完整性状态：用于诊断时应与最终展示事件数区分。

不得将某个后续分段的首条提问误用为整条会话标题。

### 5.6 缓存与版本号

V0.39 实施时必须同时处理版本与缓存：

1. 将当前构建器的产品/构建版本从 `V0.38` 更新为 `V0.39`。
2. 将界面中代表当前软件版本的显示从 `V0.38` 更新为 `V0.39`；搜索所有当前生效的版本常量、模板占位符、启动器元数据和相关测试断言，逐一确认。不得批量改写历史文档中的旧版本号。
3. 当前解析器版本为 `parserRevision = 9`，本次解析规则改变后应提升到 `10`，确保旧缓存触发重新解析。
4. 只有在缓存数据结构本身发生不兼容变化时，才提升 `cacheVersion`；若需要提升，必须同时更新缓存读取兼容检查和测试断言，不能只改写出版本。
5. 全量刷新和增量刷新必须使用同一套身份解析、分页链构建和边界归并规则。
6. 任一分段内容、大小、修改时间、压缩状态或链关系变化时，必须使对应的聚合详情缓存失效。
7. 旧缓存失效和重新构建不得导致用户备注、隐藏状态、排序偏好或来源隔离数据被删除或重置。

### 5.7 原始数据和备注保护

- 不修改、不重写、不解压覆盖任何 Codex 原始 `.jsonl` / `.jsonl.zst` 文件。
- 不删除或批量迁移备注 JSON。
- 继续保留物理分段路径与逻辑会话 ID 的映射，以兼容 V0.37 已修复的备注关联。
- 若不同分段各有备注，必须保留各自的备注目标；不得因聚合而将备注静默覆盖到另一个分段。
- 对无法唯一确定的旧备注目标，保留原记录并采取歧义保护，不得猜测编辑/删除目标。
- 不改变 Claude 或其他来源的解析规则，不引入无关 UI 重构。
