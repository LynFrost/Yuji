# 语迹 V0.25 有序列表空行分隔编号渲染修正

状态：待确认，未实施

日期：2026-06-29

## 1. 修改目标

V0.25 基于当前 V0.24，修正会话区 Markdown 有序列表的编号渲染故障。

用户反馈：

```text
有的编号为 1 2 3 4 等的内容，渲染出来变成了 1 1 1 1。
```

本版本只修正有序列表编号显示，不改变聊天记录解析，不改变搜索、复制、导出、刷新、快刷、回复框、备注等功能。

```

```

核心函数：

当前测试中已有列表相关覆盖：

但当前测试只覆盖连续行的有序列表，例如：

```text

```

尚未覆盖空行分隔的有序列表。

## 3. 根因分析

当前 `parseDeterministicBlocks()` 会按两个或更多换行切分 Markdown 块：

```text
parts[index].split(/\n{2,}/)
```

因此下面这种输入：

```text
1. 第一项

2. 第二项

3. 第三项

4. 第四项
```

会被拆成多个独立块：

```text
块 1：1. 第一项
块 2：2. 第二项
块 3：3. 第三项
块 4：4. 第四项
```

每个块都会被 `detectExplicitListType()` 识别为一个有序列表，再由 `renderListBlock()` 渲染为独立 `<ol>`：

```html
<ol class="message-list"><li>第一项</li></ol>
<ol class="message-list"><li>第二项</li></ol>
<ol class="message-list"><li>第三项</li></ol>
<ol class="message-list"><li>第四项</li></ol>
```

浏览器默认每个 `<ol>` 都从 1 开始，所以视觉上会显示为：

```text
1 第一项
1 第二项
1 第三项
1 第四项
```

结论：

```text
这是 Markdown 分块后生成多个独立 ol，且没有保留原始编号起点导致的渲染问题。
不是 CSS list-style 问题。
不是浏览器默认样式异常。
不是后端聊天记录解析问题。
```

## 4. 推荐方案

V0.25 采用最小风险修复：

```text
renderListBlock() 渲染有序列表时，读取第一条列表项的原始数字。
如果原始数字是 0 或正整数，则给 <ol> 增加 start 属性。
```

例如输入：

```text
2. 第二项
```

渲染为：

```html
<ol class="message-list" start="2"><li>第二项</li></ol>
```

或者：

```html
<ol start="2" class="message-list"><li>第二项</li></ol>
```

具体属性顺序不重要，测试只需要确认：

```text
有序列表保留 start="2"。
有序列表保留 start="3"。
无序列表不增加 start。
非法数字不进入 HTML 属性。
```

这样即使空行仍然导致多个独立 `<ol>`，每个 `<ol>` 也会从原始编号开始显示，视觉结果变为：

```text
1 第一项
2 第二项
3 第三项
4 第四项
```

## 5. 为什么不重写分块逻辑

不建议 V0.25 重写 `parseDeterministicBlocks()` 去合并空行分隔的连续列表。

原因：

```text
分块逻辑同时服务段落、代码块、引用块、表格、列表。
合并空行分隔列表可能改变用户刻意留下的列表间距。
合并逻辑需要判断列表前后是否属于同一语义列表，边界容易误判。
大改解析器可能影响已有表格、引用、代码块、搜索高亮和折叠过程渲染。
```

相比之下，`start` 属性方案：

```text
改动范围小。
符合 HTML 有序列表语义。
不会跨消息串号。
不会改变现有分块结构。
不会影响无序列表。
不会影响复制和导出原文。
```

## 6. 实现建议

建议在 `renderListBlock(text)` 内部处理。

当前逻辑大致是：

```text
检测 listType。
根据 listType 选择 ol 或 ul。
用 itemPattern 去掉列表前缀。
输出 <ol class="message-list"> 或 <ul class="message-list">。
```

V0.25 建议：

```text
1. 对 numbered 列表，读取第一条非空且匹配编号格式的列表行。
2. 用正则提取开头数字，例如 /^(\d+)\.\s+/。
3. 转成整数。
4. 只有 Number.isSafeInteger(start) 且 start >= 0 时，才认为编号有效。
5. 属性值必须来自数字解析结果，不直接拼接原始字符串。
6. bullet 列表不输出 start 属性。
```

建议伪代码：

```text
const firstLine = lines.find(line => /^\d+\.\s+/.test(line.trim())) || '';
const match = firstLine.match(/^(\d+)\.\s+/);
const start = match ? Number(match[1]) : 1;
const startAttr = listType === 'numbered' && Number.isSafeInteger(start) && start >= 0 && start !== 1
  ? ' start="' + String(start) + '"'
  : '';
return '<' + tagName + startAttr + ' class="message-list">...</' + tagName + '>';
```

是否给 `start="1"`：

```text
可省略 start="1"。
只在 start !== 1 时输出 start 属性即可。
这样 HTML 更简洁，也不改变现有连续列表的输出。
但 start="0" 应该保留，因为 0. 第零项 与默认 1. 含义不同。
```

## 8. 副作用与规避

### 8.1 独立列表仍然可能都从 1 开始

情况：

```text
用户原文确实写了多个独立列表，并且每个列表都从 1. 开始。
```

结果：

```text
仍会显示多个 1。
```

这不是副作用，而是符合原文语义。

规避：

```text
V0.25 只按原始编号显示，不尝试猜测用户是不是想延续上一组列表。
```

### 8.2 空行间距不会被压缩

情况：

```text
原文列表项之间有空行。
```

结果：

```text
渲染后仍可能是多个 <ol> 块，视觉间距可能比单个列表略大。
```

规避：

```text
本版本只修编号，不改变段落分块和间距。
如果后续需要压缩空行列表间距，可以另立版本讨论。
```

### 8.3 start 属性注入风险

风险：

```text
如果直接把原始字符串拼进 start 属性，理论上会有 HTML 属性注入风险。
```

规避：

```text
只允许 /^(\d+)\.\s+/ 提取出的数字。
转成 Number 后再输出。
只输出 0 或正整数。
不直接拼接原始文本。
```

### 8.4 大编号显示差异

情况：

```text
用户原文从 99. 或 1000. 开始。
```

结果：

```text
浏览器会按 start 属性显示对应大编号。
```

规避：

```text
这是符合 HTML 有序列表语义的行为。
只需要限制 Number.isSafeInteger，避免异常极大数字。
```

### 8.5 不处理同一块内跳号列表

情况：

```text
用户原文在同一个连续列表块中写了非连续编号，例如：

2. 第二项
5. 第五项
```

结果：

```text
V0.25 的 start 属性只能决定整个 <ol> 的起始编号。
浏览器会自动递增，因此可能显示为 2、3，而不是 2、5。
```

原因：

```text
逐项保留跳号需要为单个 <li> 输出 value 属性，或重写更完整的列表渲染逻辑。
这已经超出本次“空行分隔导致 1 1 1 1”的修复范围。
```

规避：

```text
V0.25 先不处理同一块内跳号列表。
如果未来确实需要保留每个列表项的原始编号，可另立版本讨论 li value 或完整列表解析。
```

### 8.6 不处理嵌套列表

当前 V0.24 的确定性 Markdown 渲染器并不完整支持嵌套列表。

V0.25 不新增嵌套列表能力。

原因：

```text
本次用户反馈是顶层有序列表编号被重置。
嵌套列表属于更大的 Markdown 解析能力升级，风险更高。
```

### 8.7 不影响复制与导出

复制全文和导出 MD 仍应使用原始文本。

V0.25 只影响网页正文 HTML 渲染。
