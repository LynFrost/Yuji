## 1. 问题背景

语迹近期出现 Codex 历史会话显示不完整的问题。检查发现，Codex 会话目录中存在大量以 `.jsonl.zst` 结尾的压缩会话文件，而语迹当前的索引构建器主要按普通 `.jsonl` 文件扫描，并通过普通文本流读取 JSONL 内容。

这会产生两个连续问题：

1. 文件扫描阶段没有发现 `.jsonl.zst`，相应会话不会进入索引。
2. 即使只放宽文件筛选条件，现有普通 UTF-8 文本读取逻辑也不能直接解析 Zstandard 压缩数据。

Codex 上游已加入 rollout 压缩能力：相关实现包括 [PR #25089](https://github.com/openai/codex/pull/25089)、[PR #28338](https://github.com/openai/codex/pull/28338) 和 [PR #42039](https://github.com/openai/codex/pull/42039)。这些改动表明 Codex 的会话存储可能以普通 JSONL 或 Zstandard 压缩 JSONL 形式存在。

以上上游记录能证明 Codex 已支持压缩存储机制，但不能单独确定用户设备上具体由哪个版本、配置或功能开关生成了现有压缩文件。本次修复不要求追查该启用原因，重点是让语迹可靠兼容实际存在的两种文件形式。

## 2. 本次目标

1. 让语迹发现并读取普通 Codex 会话文件 `.jsonl` 和压缩会话文件 `.jsonl.zst`。
2. 对压缩文件进行正确的 Zstandard 解压，再复用现有会话 JSONL 解析和标准化流程。
3. 让全量刷新和增量刷新都能处理两种格式，避免压缩会话被遗漏。
4. 保留会话 ID、时间、工作目录、父子/继承关系、消息顺序、标题和详情等既有语义。
5. 不修改 Codex 原始会话文件，不永久生成解压副本，不影响 Claude 会话解析。
6. 增加自动化回归测试，证明普通 JSONL 现有行为不回归，压缩 JSONL 能被正确索引。

## 3. 需求范围

### 3.1 文件发现

- 在当前代码已经支持的 Codex 会话位置中，同时识别 `.jsonl` 与 `.jsonl.zst`。
- 覆盖当前实现已扫描的活动会话、归档会话以及已支持的其他 Codex 会话来源；不得因为增加压缩格式而缩小现有扫描范围。
- 不把任意 `.zst` 文件都当成 Codex 会话。只处理符合现有 Codex rollout 命名及目录规则的 `.jsonl.zst` 文件。
- 对递归扫描、文件枚举和来源筛选沿用现有行为，不额外扫描用户未授权的目录。
- 如果同一会话的普通 `.jsonl` 与压缩 `.jsonl.zst` 同时存在，应避免重复建立两个会话。优先规则应与 Codex 的过渡态行为保持一致：优先使用普通 `.jsonl`，仅在普通文件不存在或不可用时回退到压缩文件；若当前项目的数据模型有不同的既有约定，实施前应先核实并说明，不得静默改变会话身份。

### 3.2 解压和解析

- 使用可靠的 Zstandard 解码能力读取 `.jsonl.zst`。
- 解压后的文本应直接流入现有 JSONL 逐行解析/标准化流程，避免把完整压缩文件先解压到磁盘。
- 优先使用项目可控、可随软件部署的实现；不得默认要求用户另外安装 Python、命令行解压工具或其他未声明的运行时依赖。
- 实施前先核对当前支持的 PowerShell/.NET 运行环境、仓库已有依赖和打包方式，再决定最小可维护的实现方案。如果无法避免新增依赖，必须先说明依赖、安装/分发方式、兼容性和维护成本，等待用户确认后再开发。
- 对超大会话应采用流式读取，避免一次性将整个压缩文件或解压后文本载入内存。
- 普通 `.jsonl` 继续使用原有读取路径，不应因新增压缩支持而被不必要地重新解压或改变解析方式。
- 解压后的每行仍沿用现有 JSON 解析、消息标准化、标题/摘要生成、图片引用、工具事件和会话继承处理逻辑；本次不重新设计这些功能。

### 3.3 会话身份与元数据

- 解析会话 ID 时必须正确处理 `.jsonl` 和 `.jsonl.zst` 后缀，不能把压缩扩展名误纳入会话 ID。
- 同一会话在普通格式与压缩格式间转换时，应尽可能维持稳定的会话身份，避免因扩展名变化生成重复条目。
- 文件路径、文件大小、修改时间等缓存指纹必须能识别压缩文件的变化。
- 压缩文件被更新、替换、解压恢复为普通 JSONL，或普通文件被压缩时，增量刷新应能正确判断需要重新解析的会话。
- 保留现有工作目录、来源、会话时间、标题、摘要、父会话 ID、继承位置和详情引用等字段语义，不得因文件后缀改变而丢失关系数据。
- 不修改现有用户备注、隐藏状态、pinned notes、排序偏好或其他独立持久化数据。

### 3.4 全量刷新与增量刷新

- 全量刷新必须发现并建立普通和压缩 Codex 会话的索引。
- 增量刷新必须能发现新增的 `.jsonl.zst`、识别压缩文件内容或元数据的变化，并更新对应会话。
- 当会话从 `.jsonl` 转为 `.jsonl.zst`，或反向转换时，不应出现重复会话，也不应无故丢失该会话的详情或继承关系。
- 一个损坏、截断或无法解压的压缩文件应产生可定位的诊断信息，不应被静默当作空会话。
- 单个文件读取失败不得导致其他可正常读取的会话全部从结果中消失。对已有有效索引的处理应遵循当前项目的安全更新机制，避免失败刷新用不完整结果覆盖可用数据。
- 本次不要求调查或单独修复此前发生的服务端 `Build failed`；但与本次压缩格式相关的全量/增量刷新验收必须能够明确报告成功或具体失败原因。

### 3.5 原始数据保护

- 不修改、重写、删除、移动或重命名 Codex 原始会话文件。
- 不将解压副本永久写入 Codex 会话目录或语迹项目目录。
- 如果实现确实需要临时文件，必须明确说明原因、位置、清理策略和失败恢复方式；优先避免临时落盘。
- 不读取与索引任务无关的密钥、配置秘密或其他用户文件。
- 测试使用合成的脱敏会话样本，不上传或提交用户的真实 Codex 会话内容。

## 5. 兼容性与副作用评估

### 5.1 预期收益

- Codex 将旧会话压缩后，语迹仍可发现和读取这些会话。
- 历史索引不再依赖会话文件必须保持普通 JSONL 格式。
- 全量和增量刷新对两种格式保持一致。
- 压缩/普通格式切换不会导致重复会话或丢失既有父子关系。

### 5.2 需要重点控制的风险

1. **依赖与部署风险：** Zstandard 解码器可能涉及额外依赖。必须在实施前核实当前运行环境与打包方式，不能只在开发环境可用。
2. **性能与内存风险：** 历史会话可能很大，必须流式解压，避免一次性读入整个文件。
3. **重复索引风险：** 同一会话的普通文件和压缩文件同时存在时，必须执行明确的优先级和去重规则。
4. **缓存风险：** 只新增扫描规则但不更新文件指纹或缓存修订信息，可能导致旧索引继续遗漏压缩会话。
5. **部分失败风险：** 单个坏文件不能让其他正常会话消失，也不能让索引错误地把暂时不可读的会话当成已删除。
6. **行为回归风险：** 既有普通 JSONL、会话继承、标题/摘要、图片、工具过程和消息顺序必须保持一致。
7. **外部程序兼容风险：** 不应要求 Codex 停止压缩或修改 Codex 配置来迁就语迹；语迹应兼容实际存在的文件格式。

## 7. 验收标准

以下条件必须全部满足：

1. 语迹能够扫描并读取 `.jsonl` 和 `.jsonl.zst` 两种 Codex 会话文件。
2. 压缩文件解压后复用现有消息解析逻辑，消息顺序、标题、摘要、图片、工具事件和会话继承信息正确。
3. 全量刷新与增量刷新均能处理压缩会话。
4. 普通文件与压缩文件表示同一会话时，不出现重复条目；格式切换后会话 ID 保持稳定。
5. 旧缓存不会继续阻止压缩会话进入索引。
6. 单个坏文件不会导致其他正常会话从索引中全部消失；失败有可定位诊断。
7. 不修改 Codex 原始会话文件，不永久生成解压副本。
8. 不要求用户手动安装未声明的外部解压工具；若技术上确需新增依赖，必须先由用户批准。
9. 现有普通 JSONL、Claude、继承关系、搜索、图片、备注和隐藏功能没有回归。
10. 新增测试全部通过，现有相关测试没有回归失败。
11. 只读复核最终 diff，确认修改范围符合本设计文档，没有夹带无关重构。

## 8. 明确不做的事情

- 不把 `.jsonl.zst` 简单当成 UTF-8 文本读取。
- 不只放宽文件筛选条件而不处理解压。
- 不将所有 `.zst` 文件都当成 Codex 会话。
- 不改变 Codex 原始会话文件或修改 Codex 配置来规避兼容问题。
- 不永久解压或批量重写用户历史会话。
- 不因单个坏文件而清空或覆盖其他有效会话的索引。
- 不重做现有消息解析、会话继承、列表 UI 或缓存架构。
- 不修改 Claude、WebDAV、图片处理、备注、隐藏或其他无关功能。
- 不调查此前的 `Build failed` 作为独立任务；本次只验证与压缩格式读取直接相关的构建和刷新行为。
- 不修改本地项目目录、其他 GitHub 仓库或非目标分支。
- 本文档提交后不自动修改代码、运行测试、创建 PR 或合并分支。
