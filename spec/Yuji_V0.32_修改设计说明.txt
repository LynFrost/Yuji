# Yuji V0.32 修改设计说明

> 文档状态：**需求已确认，待用户审核文档；禁止直接实施**
>
> 基线版本：`LynFrost/yuji` V0.31（当前 `master`）
>
> 目标版本：V0.32
>
> 本文档只定义 V0.32 的修改范围、技术方案、风险、副作用、测试和 Git 管理策略。**文档完成后必须停下等待用户确认，不得据此自动修改代码。**

---

## 1. 修改目标

V0.32 聚焦两项功能：

1. **图片资产托管与跨设备同步**
   - 解决当前图片依赖原始文件路径，图片移动、改名或删除后无法显示的问题。
   - 解决聊天记录同步到另一台电脑后，本地图片无法显示的问题。
   - 刷新时自动把可获取的图片保存为 Yuji 自己管理的图片资产。
   - WebDAV 已启用时，刷新后自动上传新增图片资产，但**不把“刷新”改成“自动上传整套聊天记录”**。
   - 所有可识别、可获取的图片都纳入托管，包括本地文件、Base64、HTTP/HTTPS 公网图片、localhost、127.0.0.1、局域网、公司内网等地址指向的图片。

2. **相同标题下多个子会话折叠/展开**
   - 相同标题对应多个会话分支时，在母标题右下角增加展开/收起控制。
   - 默认展开。
   - 折叠状态保存在本机浏览器，不跟 WebDAV 同步。

---

## 2. 明确不做的事情

V0.32 不包含以下扩展：

- 不把聊天记录本身改成“刷新即自动上传”。
- 不重构整个 YujiSync/v1 聊天同步协议。
- 不实现图片垃圾回收自动删除。
- 不支持 SVG 作为普通聊天图片资产。
- 不把任意普通 URL 当图片抓取；只处理**当前解析器已识别为图片引用的 URL/图片内容**。
- 不修改 `LynFrost/yuji` 之外的代码目录或文件。
- 不在本文档确认前创建开发分支、Tag、提交或修改代码。

## 3. V0.31 当前机制与问题定位

### 3.1 本地图片

V0.31 在 `Build-CodexChatIndex.ps1` 中解析图片后，本地图片记录主要依赖：

- `imageId`
- `localPath`
- `mimeType`
- `sizeBytes`

其中 `imageId` 当前与原始路径相关；网页展示时通过：

`/api/session-image`

由 `CodexChatIndexServer.py` 再根据 `localPath` 回到原文件位置读取。

因此当前本质是“保存图片引用”，不是“保存图片本身”。

直接后果：

- 原图片移动后失效。
- 原图片改名后失效。
- 原图片删除后失效。
- 相同内容在不同路径会被视为不同引用。
- 历史聊天无法形成真正稳定的图片快照。

### 3.2 WebDAV 同步

V0.31 的 WebDAV inventory 主要同步聊天 JSONL/JSON 和备注，不把本地图片本身加入上传快照。

远端来源重建索引时还会禁用本地路径图片解析，因此另一台电脑即使成功下载聊天记录，也没有原电脑的图片文件可供读取。

这不是单一显示 BUG，而是 V0.31 同步模型中尚未包含图片资产。

### 3.3 相同标题分组

V0.31 前端已经通过 `groupSessionsByTitle()` 把完全相同标题的会话聚合成一个标题组。

当 `group.sessions.length > 1` 时，会直接渲染全部子会话；当前没有组级折叠状态。

因此第二项需求无需改变后端数据结构，主要属于前端渲染和交互状态改造。

## 4. V0.32 总体设计原则

### 4.1 图片从“路径引用”升级为“内容资产”

成功获取一张图片后，不再让历史聊天依赖原始路径或原始 URL。

图片内容计算 SHA-256，并以内容摘要作为唯一资产标识：

`assetId = SHA256(image bytes)`

同一图片即使：

- 文件名不同；
- 路径不同；
- 来自不同会话；
- 来自不同电脑；

只要二进制内容相同，就复用同一资产。

### 4.2 第一次成功托管即形成历史快照

一条聊天中的图片第一次成功托管后，历史会话固定指向当时的 `assetId`。

之后即使：

- 原文件被修改；
- 原 URL 返回了另一张图片；
- 同名文件被替换；

历史聊天也不自动改变。

如果后来需要展示新内容，应作为新的图片引用/新聊天内容处理，而不是覆盖历史资产。

### 4.3 本地刷新成功与云上传解耦

刷新流程必须坚持：

**本地索引/托管成功优先，云端上传失败不能让刷新失败。**

WebDAV 图片同步属于刷新后的独立同步步骤。

## 5. 本地图片资产库设计

建议新增 Yuji 管理的图片资产库，位于现有“运行数据”体系内，而不是源码目录。

建议逻辑结构：

```text
运行数据/
└── CodexChatIndex.images/
    ├── objects/
    │   ├── 00/
    │   ├── 01/
    │   └── ab/
    │       └── <sha256>.bin
    ├── manifests/
    │   ├── local-codex.json
    │   └── local-claude.json
    └── state.json
```

说明：

- `objects`：内容寻址图片对象。
- 文件统一可使用 `.bin`，真实 MIME 由 manifest 记录，避免信任原扩展名。
- `manifests`：保存“聊天图片引用 → assetId”的稳定关系。
- `state.json`：保存迁移版本、待同步状态等轻量运行状态。
- 运行数据属于 Yuji 正常运行产生的数据，不属于源码修改范围。

### 5.1 建议的图片资产记录

示意：

```json
{
  "assetId": "<sha256>",
  "mimeType": "image/png",
  "sizeBytes": 123456,
  "createdAt": "...",
  "originType": "local|url|data",
  "originalReference": "...",
  "status": "ready"
}
```

### 5.2 聊天详情中的图片记录

成功托管后建议统一输出为：

```json
{
  "type": "managed",
  "assetId": "<sha256>",
  "mimeType": "image/png",
  "sizeBytes": 123456
}
```

不再要求网页依赖 `localPath`。

对于暂时抓取失败的图片，可保留原引用及失败状态，用于后续重试，但不得伪装成已托管。

## 6. 图片引用与资产关系的持久化

仅把 `assetId` 写进一次生成的 detail JSON 不够，因为“全量重建”可能重新解析原聊天，而原图片此时已经移动或删除。

因此必须存在独立、持久的引用映射。

### 6.1 Reference Key

每个图片引用需要稳定的 `referenceKey`。

建议由以下信息组合后哈希：

- sourceId
- 稳定会话身份
- 稳定事件/消息身份（优先使用已有 turnId/itemId/messageId）
- 图片在该事件中的序号
- 原始图片引用字符串的规范化值

对于缺少稳定消息 ID 的旧记录，可退化为：

- 会话稳定身份
- 用户事件顺序
- 图片顺序
- 原引用哈希

要求：

- 重复构建结果稳定。
- 原图片文件消失后仍能凭原聊天中的引用字符串找回既有 `assetId`。
- Parser 升级时尽量不改变已有映射。

## 7. 图片来源处理规则

### 7.1 本地文件

包括：

- 绝对路径；
- 相对 cwd 路径；
- `file://`；
- Markdown 图片路径；
- 当前文本图片解析规则识别出的本地图片。

处理：

1. 解析实际文件。
2. 校验文件存在。
3. 校验大小。
4. 校验实际文件头。
5. 计算 SHA-256。
6. 写入托管库（若已存在则复用）。
7. 更新 reference manifest。

### 7.2 Base64 图片

包括 Codex / Claude 结构化输入中的 data URL / base64 图片。

处理：

1. 解码。
2. 校验最大大小。
3. 校验真实图片格式。
4. 计算 SHA-256。
5. 写入托管库。
6. 详情中改为 managed 引用。

这样可避免长期在 session detail 中重复保存大段 Base64。

### 7.3 HTTP/HTTPS 图片

用户已明确确认：**所有图片都尝试下载**。

范围包含：

- 公网；
- localhost；
- 127.0.0.1；
- 局域网；
- 公司内网；
- 可路由的 HTTP/HTTPS 图片地址。

不因地址属于内网或本机而主动排除。

但仍需遵守基本技术约束：

- 只处理已被 Yuji 识别为图片引用的 URL。
- 不自动附带浏览器 Cookie。
- 不自动附带当前网页登录态。
- 不自动携带未知认证信息。
- 允许有限次数重定向。
- 设置连接/读取超时。
- 单图超过上限则拒绝托管。
- 下载结果必须通过真实图片文件头校验。
- URL 抓取失败不能使聊天刷新失败。
- 抓取失败后保留可重试状态，后续刷新可再次尝试。

如果 URL 必须依赖浏览器会话、登录 Cookie、临时授权头等，Yuji 无法保证一定能取得，这是“所有图片都尝试下载”下的客观技术限制。

## 8. 支持格式与大小限制

V0.32 沿用 V0.31 的单图上限：

**30 MiB / 图片**

支持：

- PNG
- JPEG / JPG
- GIF
- WebP
- AVIF

暂不支持：

- SVG

格式判断以**实际文件内容**为准，不只依赖文件扩展名或 Content-Type。

## 9. 三种刷新模式的行为

用户已确认：

- 刷新（Incremental）
- 快刷（Current）
- 全量（Full）

只要该刷新实际处理到相关会话，都执行图片托管逻辑。

### 9.1 Incremental

- 只对变化/新增会话进行正常解析。
- 对新发现或尚未托管成功的图片执行托管。
- 已存在 `referenceKey → assetId` 的历史图片优先复用，不重复读原文件/URL。

### 9.2 Current

- 对当前会话重新解析。
- 新图片立即托管。
- 已托管图片保持原快照。

### 9.3 Full

- 全量解析全部会话。
- 必须先查询持久化 image manifest。
- 即使原文件已经不存在，只要历史 referenceKey 已有 assetId，仍应恢复 managed 图片引用。
- 不得因为原图片已移动而丢失已经托管的历史图片。

## 10. V0.31 → V0.32 历史图片迁移

V0.32 第一次运行/刷新时应执行一次历史图片资产迁移。

目标：

- 尽可能把 V0.31 当前仍可访问的历史本地图片全部保存到托管库。
- 把已有 Base64 图片转换成托管资产。
- 对现有 URL 图片执行抓取。
- 建立持久 image manifest。

建议状态记录：

```text
imageMigrationVersion = 1
```

迁移完成后，普通刷新恢复增量策略。

### 10.1 迁移副作用

第一次 V0.32 刷新可能明显变慢，原因包括：

- 读取大量历史图片；
- 计算 SHA-256；
- 下载远程图片；
- 写入托管库；
- WebDAV 开启时上传新增图片。

UI 应明确表现为正常工作，不应看起来像卡死。

## 11. WebDAV 图片同步：独立 Sidecar 协议

### 11.1 不直接破坏 YujiSync/v1

V0.31 当前聊天同步协议已经包含：

- pointer
- manifest
- chatRevisionId
- notesRevisionId
- logicalFiles
- content-addressed objects

V0.32 不建议为了图片直接修改现有核心 manifest 的强校验结构。

建议增加独立图片 sidecar：

```text
<source-base>/
└── images/
    ├── current.json
    ├── manifests/
    │   └── <manifest-sha256>.json
    └── objects/
        └── ab/
            └── <asset-sha256>.bin
```

建议图片协议标识：

`YujiImageSync/v1`

优点：

- V0.31 客户端仍可按原 YujiSync/v1 处理聊天。
- V0.31 会忽略新增 `images/` 目录。
- V0.32 可以独立演进图片资产。
- 降低升级时整个聊天同步不可用的风险。

### 11.2 Image Manifest

建议包含：

- schemaVersion
- protocol
- deviceId
- sourceType
- imageManifestRevisionId
- assets
- references
- totalObjects
- totalBytes
- generatedAt

其中：

- `assets` 描述 assetId、mimeType、size。
- `references` 描述 referenceKey 与 assetId 的映射。

## 12. “刷新自动上传图片”的精确定义

用户已确认：

**刷新时自动上传新增图片，但不自动上传整套聊天记录。**

执行规则：

1. 本地刷新先完成。
2. 新增图片先完成本机托管。
3. 若 WebDAV 未开启：到此结束。
4. 若 WebDAV 已开启：
   - 自动启动/触发图片 sidecar 增量同步。
   - 只上传缺失的图片对象和新的图片 manifest。
   - 不自动调用“整套聊天上传”的原逻辑。
5. 图片云上传失败：
   - 不回滚本地刷新。
   - 不删除本地托管图片。
   - 记录 pending 状态，允许后续刷新或手动上传继续补齐。

### 12.1 WebDAV 正忙时

V0.31 WebDAV 任务管理目前存在单任务/互斥约束。

V0.32 不应为了图片同步打断正在进行的：

- 手动聊天上传；
- 下载；
- 其他 WebDAV 任务。

建议：

- 如果 WebDAV 正忙，刷新仍正常成功。
- 把图片同步标记为 pending。
- 任务空闲后由下一次刷新、手动上传或明确的补偿触发继续同步。
- 不制造并发写 pointer/manifest 的竞态。

---

## 13. 手动聊天上传与图片的关系

虽然刷新只自动上传图片，但用户手动执行“上传聊天”时，应同时做一次图片完整性检查：

- 当前聊天上传涉及的已托管图片是否已存在云端。
- 缺失图片先补上传。
- 图片 manifest 更新。
- 再完成/确认聊天上传结果。

目的：

避免出现“聊天已经正式上传，但它引用的图片因为之前自动同步失败而长期缺失”。

---

## 14. 另一台电脑下载后的图片恢复

V0.32 下载远端来源时：

1. 按现有 YujiSync/v1 下载聊天。
2. 检查该来源是否存在 `YujiImageSync/v1` sidecar。
3. 下载 image manifest。
4. 只下载本机缺失的 asset objects。
5. 按 SHA-256 校验。
6. 写入本机托管图片库。
7. 远端索引重建时加载 image manifest。
8. 将聊天中的对应图片恢复成 `type=managed`。
9. 页面通过 Yuji Server 读取本机托管资产，不依赖原电脑路径。

如果远端没有图片 sidecar：

- 兼容 V0.31 行为。
- 聊天仍可正常下载。
- 图片可显示能力按现有条件降级。

## 15. 图片服务 API

建议扩展现有图片服务，而不是让浏览器直接访问运行数据文件。

可以选择：

### 方案 A：扩展现有 `/api/session-image`

支持：

- legacy local image
- managed asset

优点：前端改动较少。

### 方案 B：新增 `/api/image-asset`

例如：

`/api/image-asset?sourceId=...&assetId=...`

优点：语义更清晰。

推荐 **方案 B**，同时保留 V0.31 legacy endpoint 兼容已有本地图片记录。

Server 必须：

- 校验 assetId 为 64 位十六进制 SHA-256。
- 只允许读取托管图片目录。
- 不接受任意文件路径。
- MIME 从受信 manifest/文件头获得。
- 继续执行大小和文件头校验。

---

## 16. 图片失败状态

图片处理不应是“全有或全无”。

建议状态至少区分：

- ready：已托管。
- pending：等待抓取/等待云同步。
- unavailable：原始来源当前无法访问。
- too-large：超过 30 MiB。
- invalid-format：文件内容不是支持图片。
- download-failed：URL 下载失败。
- sync-failed：本机已有，云端同步失败。

原则：

- 单张图片失败不影响其他图片。
- 单张图片失败不影响聊天解析。
- 云端图片同步失败不影响本地刷新成功。
- 后续刷新允许重试可恢复错误。

---

## 17. 图片删除与垃圾回收

V0.32 暂不主动删除托管图片对象。

原因：

- 历史 reference 可能仍引用该图片。
- 多个会话可能共用相同 assetId。
- 云端多设备状态可能不同步。
- 错误 GC 的代价远高于占用额外空间。

因此 V0.32 采用：

**只增量新增 + 内容去重 + 暂不自动 GC**

后续版本可单独设计“引用计数/可达性扫描 + 安全垃圾回收”。

## 18. 相同标题子会话折叠设计

### 18.1 当前结构

V0.31：

- `groupSessionsByTitle()` 已存在。
- 完全相同标题被归入同一个 group。
- 单会话：只显示母标题。
- 多会话：母标题下总是显示所有 `.title-group-sessions`。

### 18.2 V0.32 目标行为

只有：

`group.sessions.length > 1`

时才显示折叠箭头。

默认状态：

**展开**

交互：

- 点击母标题主体：保持 V0.31 行为，进入该组默认/第一个会话。
- 点击右下角箭头：只切换展开/收起，不切换当前会话。
- 收起时隐藏所有子会话行。
- 当前激活会话如果属于已收起组，母标题仍保持 active 状态。

### 18.3 DOM 结构要求

V0.31 的 `.title-group-head` 本身是 button。

V0.32 不允许在 button 内嵌 button。

推荐结构：

```html
<section class="title-group">
  <div class="title-group-header">
    <button class="title-group-head">...</button>
    <button class="title-group-toggle">...</button>
  </div>
  <div class="title-group-sessions">...</div>
</section>
```

这样标题点击与折叠点击互不干扰，也符合键盘可访问性要求。

### 18.4 箭头位置

用户指定：

**母标题右下角**

同时当前备注状态圆点占用右上区域，因此右下角不会与备注标识冲突。

箭头可采用：

- 展开：向下；
- 收起：旋转到侧向；

或统一图标通过 CSS transform 旋转。

要求有：

- `aria-expanded`
- 明确 `title`
- 键盘 Enter/Space 可操作

## 22. 副作用与风险

### 22.1 本机磁盘占用增加

原因：历史图片由“引用”变成“真正保存”。

控制：

- SHA-256 内容去重。
- V0.32 暂不自动 GC，优先保证历史完整性。

### 22.2 WebDAV 空间增加

图片将开始真正上传。

控制：

- 内容寻址去重。
- 已存在对象不重复传。
- 上传 journal/状态记录用于断点补偿。

### 22.3 第一次 V0.32 刷新耗时增加

尤其历史聊天多、图片多、URL 多时。

这是迁移成本，不应误判为异常。

### 22.4 网络流量增加

刷新可能触发：

- URL 图片下载。
- WebDAV 图片上传。

特别是内网/公网大量图片时会更明显。

### 22.5 隐私边界扩大

用户已明确确认“所有图片都下载”。

因此当聊天引用：

- 公司内网图片；
- localhost 图片；
- 局域网图片；

Yuji 成功抓取后，在 WebDAV 已开启的情况下会把这些图片作为托管资产同步到用户配置的云端。

这是 V0.32 与 V0.31 相比最重要的隐私行为变化之一，README/版本说明中必须明确。

### 22.6 认证型 URL 不保证成功

因为 Yuji 不应自动偷取浏览器 Cookie 或未知凭据。

因此“所有图片都下载”的实现含义是：

**所有已识别图片地址都尝试获取，而不是保证所有受认证保护的资源都一定成功。**

### 22.7 云端存在孤立图片

V0.32 暂不做自动 GC，因此聊天删除后可能留下旧 asset object。

这是有意选择的安全策略。

### 22.8 协议复杂度增加

通过独立 `YujiImageSync/v1` sidecar 控制风险，避免直接破坏稳定的聊天协议。

## 26. 当前结论

V0.32 的核心不是简单“把图片上传云端”，而是把 Yuji 的图片模型从：

**依赖原始路径/原始 URL 的临时引用**

升级为：

**本地内容寻址托管 + 稳定引用映射 + 独立 WebDAV 图片 sidecar + 跨设备恢复**

这样才能同时彻底解决：

1. 图片移动后失效；
2. 图片跨电脑同步后失效；

并且不破坏 V0.31 已经稳定的聊天同步语义。

标题折叠则保持为纯前端、低耦合改造，不扩大后端数据结构。
