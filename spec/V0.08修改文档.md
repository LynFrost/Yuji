# Open-CodexChatIndex V0.08 修改文档

状态：已实施并验收

日期：2026-05-07

## 1. 修改目标

V0.08 的目标是大幅缩短刷新耗时，让用户可以用 Codex CLI 继续对话，再用 Open-CodexChatIndex 快速查看最新结果。

本版本重点优化：

```text
刷新不再默认全量重建全部聊天记录。
新增当前会话快刷能力，优先服务 CLI 对话后的即时查看。
普通刷新改为智能增量刷新，只解析新增或变化的 JSONL。
保留全量重建作为兜底修复入口。
打开的 cmd 窗口增加明确标题，便于识别本地服务。
```

本版本不改变 V0.07 已确认的会话阅读规则，不影响提问定位、上下键切换、回到顶部后自动聚焦、只看提问、复制全文、导出 MD、复制路径、复制 SESSION、过程懒渲染和滚动流畅性。

## 2. 当前刷新慢的原因

V0.07 的刷新路径是：

```text
浏览器点击“刷新”。
前端调用 /api/refresh。
CodexChatIndexServer.py 调用 Build-CodexChatIndex.ps1。
Build-CodexChatIndex.ps1 重新扫描全部 .codex\sessions 和 .codex\archived_sessions。
逐个解析所有 *.jsonl。
重新写出全部会话详情分片。
重新写出 CodexChatIndex.data.json。
前端接收完整新索引并重新渲染。
```

当前数据规模大约为：

```text
会话数量：约 1910 条。
源 JSONL 总大小：约 926 MB。
详情分片总大小：约 180 MB。
总索引文件大小：约 3 MB。
```

因此刷新需要几分钟的核心原因不是浏览器按钮或弹窗慢，而是每次刷新都在做全量构建。

V0.08 需要从架构上避免日常刷新走全量构建。

## 3. 刷新模式设计

V0.08 建议将刷新拆成三种能力。

### 3.1 当前会话快刷

新增“快刷当前”能力。

用途：

```text
用户正在用 CLI 对当前 session 对话。
对话结束后，希望本软件快速看到当前会话新增内容。
```

行为：

```text
前端把当前选中会话的 path 发送给服务端。
服务端只读取并解析这一条 JSONL。
只更新这一条会话的详情分片。
只更新总索引中这一条会话的标题、更新时间、用户数、回答数、摘要等元信息。
前端只刷新当前会话详情和必要的索引状态。
```

预期收益：

```text
不用扫描和解析全部 900 MB 以上历史记录。
日常 CLI 追加后查看，应从几分钟降到几秒级。
```

限制：

```text
只保证当前打开的会话更新。
不会负责发现其他新会话。
不会负责清理已删除会话。
```

### 3.2 智能增量刷新

将当前“刷新”改为智能增量刷新。

用途：

```text
用户希望同步新增会话、变化会话和列表信息。
但不希望每次都全量重建。
```

行为：

```text
扫描 sessions 和 archived_sessions 下的 JSONL 文件列表。
读取每个文件的路径、大小、最后修改时间。
与上次缓存清单比对。
只解析新增或发生变化的 JSONL。
未变化的会话复用已有详情分片和索引元信息。
重新生成 CodexChatIndex.data.json。
删除已经不存在的会话对应索引项和详情分片。
```

预期收益：

```text
如果只新增或修改少量会话，刷新只处理少量文件。
大多数日常刷新应明显快于 V0.07 全量刷新。
```

限制：

```text
仍然需要扫描文件列表和读取文件元信息。
如果大量历史文件同时变化，耗时会接近全量重建。
```

### 3.3 全量重建

保留全量重建能力，但不作为日常刷新默认入口。

用途：

```text
首次生成数据。
缓存清单丢失或损坏。
用户怀疑增量结果不准确。
大量文件移动、删除或归档后需要修复索引。
版本升级后数据结构发生变化。
```

界面上可以使用明确名称：

```text
全量重建
```

并通过提示说明：

```text
全量重建会重新扫描和解析全部聊天记录，可能需要较长时间。
```

## 4. 增量缓存设计

在共享运行数据目录下增加轻量缓存清单，例如：

```text
软件\运行数据\CodexChatIndex.cache.json
```

缓存清单建议记录：

```text
cacheVersion
builderVersion
generatedAt
files[]
```

每个文件记录：

```text
path
id
detailFileName
sizeBytes
lastWriteTimeUtc
archived
cwd
title
summary
createdAt
createdLocal
updatedAt
updatedLocal
userCount
assistantCount
messageCount
source
modelProvider
hasImageReference
```

判断文件是否需要重新解析时，优先使用：

```text
path
sizeBytes
lastWriteTimeUtc
```

如果这些信息都未变化，则认为该 JSONL 未变化，直接复用缓存元信息和已有详情分片。

如果缓存版本与当前构建器版本不兼容，应自动退回全量重建或提示用户执行全量重建。

## 5. 服务端接口设计

V0.08 建议服务端提供三个刷新接口。

```text
POST /api/refresh-current
```

用于当前会话快刷。请求体包含当前会话 path 或 key。

```text
POST /api/refresh
```

用于智能增量刷新。保持原有按钮语义，但内部不再默认全量构建。

```text
POST /api/rebuild
```

用于全量重建。作为兜底修复入口。

接口返回应包含：

```text
ok
mode
message
scannedCount
parsedCount
reusedCount
deletedCount
elapsedMs
data
currentDetail
```

前端可以用这些字段展示自动消失的提示，例如：

```text
快刷当前完成：解析 1 条，会话已更新，用时 1.8 秒。
增量刷新完成：扫描 1910 条，解析 2 条，复用 1908 条，用时 4.6 秒。
全量重建完成：解析 1910 条，用时 3 分 12 秒。
```

## 6. 前端交互设计

会话区顶部按钮建议调整为：

```text
快刷当前
刷新
全量重建
路径
SESSION
导出 MD
```

其中：

```text
快刷当前：只更新当前打开的会话。
刷新：执行智能增量刷新。
全量重建：执行完整重建，作为修复入口。
```

刷新过程中应保持现有 loading 动效，并禁止重复点击同一个刷新动作。

不同刷新模式应有清晰提示：

```text
快刷当前中...
刷新中...
全量重建中...
```

完成提示使用自动消失 toast，不使用需要确认的 alert。

刷新完成后应尽量保持：

```text
当前目录不变。
当前标题不变。
当前会话不变。
当前提问定位不变。
上下键切换仍可直接使用。
如果当前会话新增了最新提问或回答，当前阅读位置不应被强行拉走，除非用户正在查看最后一个提问。
```

## 7. 安全写入和并发读取

CLI 可能正在写入 JSONL，本软件刷新时需要避免读到半成品导致失败。

读取规则：

```text
继续使用允许 ReadWrite 共享的方式读取 JSONL。
逐行解析 JSON。
解析失败的空行或不完整末尾行跳过。
中间行如果解析失败，记录警告但不让整个刷新失败。
```

写出规则：

```text
详情分片先写入临时文件，再替换正式文件。
CodexChatIndex.data.json 先写入临时文件，再替换正式文件。
CodexChatIndex.cache.json 先写入临时文件，再替换正式文件。
```

这样可以避免浏览器刚好读取到半写入的 JSON 文件。

## 8. 删除、归档和异常处理

智能增量刷新需要处理文件消失的情况。

规则：

```text
缓存中存在但本次扫描不到的 JSONL，应从索引中移除。
对应详情分片可以删除。
如果删除失败，不阻塞刷新，但提示有残留文件。
```

归档变化规则：

```text
如果同一会话路径从 sessions 变为 archived_sessions，按路径变化识别为新文件。
旧路径从索引移除。
新路径按新增会话解析。
```

缓存异常规则：

```text
缓存文件不存在：执行全量重建并生成缓存。
缓存 JSON 解析失败：提示缓存损坏，并建议全量重建。
缓存版本不兼容：自动全量重建或提示全量重建。
详情分片缺失但缓存认为未变化：重新解析该 JSONL。
```

## 9. 性能目标

V0.08 的性能目标按场景区分。

当前会话快刷：

```text
小型和中型当前会话尽量控制在 5 秒以内。
超大当前会话也必须明显快于全量刷新。
```

智能增量刷新：

```text
只有少量会话变化时，尽量控制在 5 秒以内。
扫描全部文件元信息可以接受，但不能逐条解析全部 JSONL。
```

全量重建：

```text
允许耗时较长。
必须明确告知用户这是修复入口，不是日常刷新入口。
```

页面交互：

```text
刷新完成后滚动不能变卡。
不能因为缓存策略把所有详情内容常驻内存。
不能一次性向页面注入大量隐藏 DOM。
```

## 10. 不改变的功能

V0.08 不能影响以下既有功能：

```text
进入会话后自动聚焦最后一个提问。
点击标题后直接使用上下键切换提问。
回到顶部后自动聚焦第一个提问。
只看提问。
搜索当前会话。
过程摘要默认懒渲染。
展开过程后再渲染过程明细。
收起过程后释放过程明细 DOM。
复制全文。
导出 MD。
复制路径。
复制 SESSION。
标题区选中提示。
目录区和标题区筛选、排序。
回滚分支不进入默认有效事件流。
UTC 时间正确显示为本地时间。
```

尤其需要保证：

```text
快刷当前后，复制全文和导出 MD 包含完整最新内容。
快刷当前后，搜索范围与当前有效事件流一致。
增量刷新后，标题区排序和分支分组仍正确。
增量刷新后，已删除会话不应继续出现在列表里。
```

## 11. cmd 窗口标题

V0.08 需要修改启动命令文件：

```text
软件\软件版本_V0.08\Open-CodexChatIndex.cmd
```

打开 cmd 窗口后应设置明确标题，例如：

```text

```

目的：

```text

避免误关其他命令行窗口。
便于验收后手动关闭服务窗口。
```

## 12. 副作用和风险

增量缓存会增加刷新逻辑复杂度。相比 V0.07 的全量重建，V0.08 需要处理缓存命中、缓存失效、文件删除、详情分片缺失、缓存版本升级等情况。

如果缓存判断错误，可能出现旧内容未更新。为降低风险，必须使用路径、大小、最后修改时间共同判断；详情分片缺失时必须强制重新解析；保留全量重建兜底。

当前会话快刷只更新当前会话，不保证发现其他新会话。用户如果需要同步整个列表，应使用智能增量刷新。

如果 CLI 正在写入 JSONL，刷新可能暂时读不到最后一条未写完的事件。这个行为可以接受，因为下次快刷会补上；不应为了读取半行而导致整个刷新失败。

超大单会话快刷仍可能耗时数秒，尤其是几十 MB 的 JSONL。V0.08 第一阶段先做“只解析当前文件”，不直接做“只解析新增尾部”的复杂逻辑。后续如果仍慢，再考虑尾部增量读取。

智能增量刷新仍需要扫描所有 JSONL 的文件元信息。这个扫描比解析全部 JSONL 快很多，但如果 OneDrive、杀毒软件或磁盘状态较慢，仍可能有少量等待。

界面增加“快刷当前”和“全量重建”后，按钮会比 V0.07 多。需要通过按钮名称和提示降低误用概率，不应让用户误以为全量重建是日常刷新。
