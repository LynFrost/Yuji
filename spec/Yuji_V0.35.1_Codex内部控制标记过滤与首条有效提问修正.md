## 1. 本次三项需求总览

本次 V0.35.1 文档包含用户已提出的三项需求。三项都属于语迹会话列表与会话内容识别的修正，必须一并纳入设计和验收，不得只实现第三项。

### 1.1 子会话不单独显示标题；每个会话节点一行、只显示描述

会话列表中的每个实际会话节点只占一行，并且这一行只显示该会话自己的描述。

- 根会话、普通会话和子会话都遵守“一条会话节点 = 一行描述”的规则。
- 子会话不再额外显示一行独立标题，也不重复显示父会话标题；应显示该子会话自身的描述。
- 描述以该会话经过内部控制信息过滤后的第一条有效用户提问为依据，不能继承父会话的标题或描述。
- 不在会话节点下方再追加第二行时间、问答数量或其他统计元信息。相关数据若仍被其他功能使用，可以保留在索引数据中，但不在该列表节点中显示。
- 描述过长时保持单行并使用省略号；鼠标悬停时通过提示文字展示完整描述。
- 现有同标题母标题/分组标题及其折叠能力继续保留；分组标题不能替代子会话自身的描述，也不能因此把真实父子关系变成仅按标题分组。
- 单击某行仍必须打开该行对应的实际会话，不能因树形缩进或描述相同而打开父会话。
- 保留当前会话选中与高亮、备注、隐藏状态、pinned notes、搜索、排序和折叠等既有功能。
- 本需求改变的是会话列表的展示方式，不要求删除索引中的标题字段，也不改变会话 ID、父子关系或原始日志。

### 1.2 继承关系增加清晰可见的树形连线

真实父子会话之间应使用类似用户提供截图的树形连接线，而不是只靠缩进、箭头或相同标题表达关系。

连线的视觉规则：

- 根会话作为父节点；其直接子会话通过分支线连接到父节点。
- 同一父节点下的多个子会话显示为同级分支。
- 在连续的兄弟节点旁显示纵向主线，并用横向短线连接到每个子会话节点。
- 最后一个子节点的连线在该节点处自然结束，不继续延伸成不存在的后续分支。
- 多级继承链按层级持续缩进，纵向线与横向分支线保持连续，能看出父、子、孙节点之间的真实层级。
- 连线应与每个会话的一行描述布局协调，不得导致节点文字错位、遮挡或意外换成两行。
- 连线只能依据已确认的会话级父子关系生成；不能根据相同标题、相近时间或文本相似度虚构连接。
- 对父会话缺失、关系未知或父节点被筛选隐藏的情况，应保留必要的关系状态提示，不得把子节点错误连接到其他会话。
- 折叠、搜索、筛选、排序、来源/工作目录切换后，连线应与当前实际呈现的节点一致；这些操作不能修改真实关系数据。
- 保留会话节点的点击、选中、高亮、备注、隐藏和母标题折叠行为；连线本身不能拦截节点点击。

### 1.3 过滤 Codex 自动插入、被误认成提问的内部控制标记

用户截图中的会话开头出现以下内容：

\`\`\`text
<external_codex_apps_open_page>{"page_id":null}</external_codex_apps_open_page>
\`\`\`

该内容被语迹误识别为普通用户消息，并影响会话标题/描述。用户表示自己没有主动发送这段内容，怀疑它是 Codex 或相关外部应用集成自动加入的内部控制信息。

当前可以确认的是语迹错误地将这段内容呈现为普通用户提问；具体由 Codex 的哪个组件产生，仍需以原始 rollout JSONL 记录为准，不预先认定来源。

处理原则：

- 只过滤经过源记录核实、可明确识别的内部控制块。
- 纯内部控制消息不进入正常聊天详情、标题/描述、用户消息计数或提问搜索内容。
- 如果控制块后面还有真实提问，应移除控制块并保留真实提问。
- 如果控制标记与真实提问位于同一条消息中，只移除可确认的控制块，保留其余文本。
- 如果开头有多条纯内部控制消息，可以逐条过滤；但不得仅按“位于开头”这一位置规则删除真实提问。
- 标题和描述应来自过滤后的第一条有效用户提问。
- 不对原始 Codex 日志文件做任何修改。

## 2. 现有代码与原因判断

已只读检查 `feature/v0.35` 分支中的相关代码：

- `Build-CodexChatIndex.ps1`
- `tests/Build-CodexChatIndex.Tests.ps1`

现有解析器已有 `Remove-CodexInjectedContextPrefix`，并通过 `$script:CodexInjectedContextTagNames` 维护已知的内部上下文标记列表。该函数能够连续移除消息开头的已知内部上下文块，并保留其后真实提问。

目前的已知标记列表没有包含 `external_codex_apps_open_page`。当该标记未被识别时，它可能作为普通用户消息进入标准化事件列表。之后，Codex 会话标题和摘要会从标准化用户事件中取第一条消息，因此内部标记可能成为标题与摘要。

Codex 用户消息目前存在多种源记录格式，至少包括：

- `response_item` 中的 `message / role=user`
- `event_msg / user_message`
- `item_completed` 中的 `UserMessage`

现有过滤函数已被这些解析路径使用。本次优先复用现有机制，不另建一套互不一致的过滤流程。

以上是代码层面的原因判断。实施前仍需检查实际原始记录，确认截图中的标记确实以可识别的完整标记块出现在用户消息开头。

## 3. 三项需求的实现目标与核心原则

### 3.1 修改目标

1. 每个实际会话节点在列表中只占一行，并且只显示该会话自身的描述。
2. 子会话不额外显示独立标题或父会话标题；描述使用该子会话自己的第一条有效用户提问。
3. 在已确认的父子会话之间绘制清晰、连续的树形连线，表达真实的多级继承结构。
4. 将已确认的 external_codex_apps_open_page 内部控制标记纳入现有 Codex 注入上下文过滤机制。
5. 纯内部控制消息不再作为普通用户提问显示，也不污染标题、描述、统计或搜索内容。
6. 多条连续内部控制消息均可被过滤，但所有真实用户提问都必须保留。
7. 兼容现有会话点击、选中、折叠、备注、隐藏、pinned notes、搜索、排序、图片、消息解析和缓存机制。

### 3.2 Codex 内部控制消息过滤不采用“删除前 N 条、保留最后一条”的固定规则



不能按消息位置盲目删除会话开头的第一条或前几条用户消息，也不能无条件只保留开头序列中的最后一条。

正确规则是：

**识别并过滤有明确依据的内部控制内容，再从剩余有效用户消息中选择第一条作为标题和摘要来源。**

因此：

- 开头有 1 条纯控制消息：过滤该消息，保留后续真实提问。
- 开头有多条纯控制消息：逐条识别并过滤，保留后续真实提问。
- 开头连续出现多条真实用户提问：全部保留，第一条真实提问仍作为标题来源。
- 控制标记与真实提问位于同一条消息中：移除可确认的前置控制块，保留后续真实提问。
- 无法可靠识别为控制内容时：不得仅凭消息位置、文本相似度或“看起来不像问题”就删除消息。

### 3.3 列表展示、树形连线与解析数据的边界

- 会话列表的“描述”是显示字段，不应为了隐藏独立标题而删除底层会话 ID、标题元数据或父会话 ID。
- 每个节点的描述必须对应当前节点自己的会话内容。子会话不能直接复用父会话的标题或首条提问作为自己的描述。
- 内部控制标记过滤必须先于第一条有效提问的选择，避免控制消息同时污染会话描述和 Codex 标题。
- 树形连线使用索引中已确认的会话级父子关系；同标题分组只是一种现有展示能力，不能作为连线依据。
- 对无法确认父会话的节点，仍按单行描述正常显示，但不绘制推测性的父子连线。
- UI 改动不得改变会话事件内容、消息顺序、备注目标或父子关系数据。

## 4. 详细实现要求

### 4.1 先确认真实源记录格式

实施时先从出现问题的会话原始 rollout JSONL 中只读核对：

- 标记所在的源记录类型。
- 标记是独立用户消息，还是某条用户消息中的前置内容。
- 标记的开闭标签和载荷结构。
- 标记后面是否存在真实提问。
- 同一会话是否有连续出现多个内部标记的情况。

不得修改、重写或清理原始 Codex 会话文件。测试应使用脱敏的合成 fixture，或不包含敏感对话内容的最小化样例。

### 4.2 扩展现有标记列表

在确认源记录格式与截图相符后，将以下标签加入现有的 `$script:CodexInjectedContextTagNames`：

```text
external_codex_apps_open_page
```

过滤逻辑应沿用 `Remove-CodexInjectedContextPrefix` 的既有设计：

- 允许标签内部载荷包含 JSON 等内容，不将 `page_id` 是否为 `null` 作为唯一判断条件。
- 只有标签名称、开闭结构和消息位置符合已确认的内部上下文格式时，才将其作为控制块移除。
- 支持连续出现多个已知前置控制块。
- 移除前置控制块后，保留后续所有真实提问文本及其原有顺序。
- 不对任意文本执行全局字符串替换，不因消息中任意位置出现相同字符串就删除整条消息。
- 如果原始记录显示的结构与当前预期不同，应先按真实结构调整设计与测试，不得用宽泛正则表达式猜测删除范围。

### 4.3 纯控制消息的处理

如果移除前置控制块后，消息正文为空或只剩空白，且没有需要保留的图片内容，则不应生成普通 `user` 事件。

该消息因此不应进入：

- 聊天详情中的正常用户消息列表。
- 用户消息计数。
- 第一条有效用户提问的选择结果。
- 标题与摘要生成。
- 提问搜索字段及其他由有效用户消息生成的派生字段。

如果消息仍包含真实文本，必须保留该文本。如果消息没有文本但确实带有图片，则应继续沿用现有图片消息规则，保留图片及对应的图片占位显示，不能因为文本过滤而丢失图片。

### 4.4 标题、摘要和计数

会话标题与摘要必须基于完成内部上下文过滤、去重后的有效事件计算。

- 标题：取第一条有效用户提问的首行，继续沿用现有标题截取规则。
- 摘要：取第一条有效用户提问，继续沿用现有摘要长度与格式规则。
- 用户消息数量：不计入被过滤掉的纯控制消息。
- 提问搜索字段：不包含被过滤掉的控制标记。
- 详情事件：不再包含被过滤掉的纯控制消息。
- 图片引用统计：继续依据过滤后实际保留的有效图片消息计算。

如果会话没有任何有效用户提问，不得退回使用控制标记作为标题或摘要；应沿用现有文件名等回退规则。若会话同时没有有效助手事件，是否跳过空会话也继续遵守现有逻辑，不额外改变会话保留策略。

### 4.5 所有 Codex 用户消息解析路径保持一致

必须确认以下路径均执行一致的过滤规则：

1. `response_item` 的用户消息。
2. `event_msg / user_message`。
3. `item_completed / UserMessage`。

不能只修复其中一种源记录格式，否则同一类标记在不同 Codex 版本或记录格式下仍可能泄漏。

本次不修改 Claude 的解析路径，也不改变现有用户消息去重规则。控制标记过滤应在消息进入最终标准化事件集合前完成，避免它先参与标题选择、统计和搜索索引。

### 4.6 缓存与旧索引兼容

本次会改变解析结果，现有索引或共享缓存可能仍保存着旧标题、旧摘要和旧详情。

实施时必须检查现有缓存失效机制，并采用最小且符合项目现状的版本调整方式，例如更新解析器修订号或构建器版本；只有在确有必要时才调整缓存结构版本。

验收时必须证明：

- 旧缓存不会让错误标题长期保留。
- 重新构建后，受影响会话的标题、摘要、计数、搜索内容和详情均已修正。
- 不需要修改原始 Codex 日志文件。
- 缓存重建不会破坏备注、隐藏状态、排序偏好或其他用户数据。

不能仅以新建测试会话正确为验收通过的依据。

**tests/Build-CodexChatIndex.Tests.ps1 及相关 UI 测试/夹具**

- 验证列表单行展示、子会话使用自身描述、长文本省略/悬停提示，以及树形连线结构。
- 验证父会话缺失、关系未知、筛选/折叠后连线仍正确。
- 验证原始日志未被修改，且备注等用户数据不丢失。

### 5.2 原则上不需要修改

- CodexChatIndexServer.py：除非验证发现服务层存在独立的旧缓存或数据转换问题，否则不扩大修改范围。
- Claude 解析：本次新增的控制标记过滤只针对已核实的 Codex 格式；不得将 Codex 标签规则无差别套用到 Claude。
- WebDAV 同步、图片托管协议及其他 Provider：与本次三项需求无直接关系，不应修改。
- 现有备注、隐藏、排序和 pinned notes 的持久化格式：除非测试证明有必要，否则保持不变。

如果实施前的进一步核查证明必须扩大范围，应先说明原因和副作用，再由用户确认。

| T13 | 描述很长 | 仍保持单行并显示省略号；悬停可以查看完整描述 |
| T14 | 一个父会话有多个子会话，并存在多级孙会话 | 纵向主线、横向分支线和缩进层级清晰；最后一个子节点的连线正确结束 |
| T15 | 搜索/筛选、折叠、排序或切换来源后重新呈现树形列表 | 连线与可见节点一致，不误连节点、不改变真实父子关系 |
| T16 | 点击带有连接线和缩进的子会话行 | 打开该子会话自身；选中、高亮、备注和隐藏行为正常 |

## 7. 验收标准

全部满足以下条件才算完成：

### 7.1 会话列表单行显示

1. 根会话、普通会话和子会话的每个实际节点都只占一行。
2. 每行只显示对应会话自身的描述，不再在节点下方追加时间、问答数量等第二行元信息。
3. 子会话描述来自其自身过滤后的第一条有效用户提问，不使用父会话标题或父会话描述。
4. 长描述单行省略，悬停可查看完整描述。
5. 原有母标题/同标题分组折叠、节点点击、选中高亮、备注、隐藏、pinned notes、搜索和排序均正常。
6. 隐藏展示标题不会删除底层会话 ID、标题元数据或父子关系字段。

### 7.2 继承关系连线

1. 已确认的父子会话之间有清晰可见的树形连线，能够识别根节点、子节点、孙节点和多个兄弟分支。
2. 连线使用连续纵向主线和连接到节点的横向分支线；最后一个子节点的连线正确结束。
3. 连线只来自真实可验证的会话级父子关系，不根据相同标题、相近时间或文本相似度推测。
4. 父会话缺失、关系未知或父节点被过滤时，不误连到其他会话。
5. 搜索、筛选、折叠、排序和来源/工作目录切换不会改变关系数据，连线始终与当前展示结构一致。
6. 连线不遮挡文字，也不影响会话点击、选中、高亮和其他既有交互。

### 7.3 Codex 控制标记过滤与内容完整性

1. 截图中出现的纯 external_codex_apps_open_page 控制消息不再显示为普通用户提问。
2. 会话标题、描述、摘要、计数和提问搜索内容不再被该控制标记污染。
3. 多条连续内部控制消息均能正确过滤，不需要假设只会出现一条。
4. 第一条真实用户提问及后续真实提问均得到保留；控制标记与真实提问同条时只移除已确认的控制块。
5. 正常用户消息、图片、助手消息和工具事件不受影响。
6. 三种 Codex 用户消息源记录格式的处理结果一致。
7. 旧索引或缓存能够通过既有机制更新，用户备注等持久化数据不丢失。
8. 原始 Codex 会话文件没有被修改。

### 7.4 回归

1. 现有搜索、筛选、排序、来源切换和工作目录切换正常。
2. 现有标题折叠、备注、隐藏、pinned notes 和会话选择正常。
3. Codex、Claude 和 WebDAV 已支持的读取/同步功能不发生无关回归。
4. 新增回归测试通过，且现有相关测试没有回归失败。

## 8. 明确不做的事情

- 不盲目删除会话开头固定数量的用户消息。
- 不采用“只保留开头序列最后一条”的通用规则。
- 不过滤所有包含 XML 标签、JSON 或英文标记的普通用户消息。
- 不通过标题相似度、消息位置或文本启发式猜测来删除内容。
- 不改变真实提问的排序和原始消息顺序。
- 不为了单行显示而删除底层会话 ID、标题元数据、父子关系或原始事件。
- 不把父会话标题当作子会话描述，不在单行描述下方追加第二行时间/统计元信息。
- 不根据相同标题、相近时间或文本相似度绘制虚假的继承连线。
- 不因折叠或筛选而改写真实父子关系。
- 不修改 Codex 或 Claude 原始会话文件。
- 不修改与本问题无关的其他 Provider、WebDAV 或图片处理逻辑。
- 不修改本地项目目录或其他 GitHub 仓库。
